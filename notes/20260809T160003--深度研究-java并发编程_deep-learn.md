# Java 并发编程 深度认知学习计划

> **领域类型**：T 型（技术/工程——有明确对错，代码能跑通/跑不通，demo 可验证），带少量 R 型色彩（底层有 JMM、管程等理论模型）
> **目标深度**：C. 能判断——学完能独立判断新并发技术（虚拟线程、结构化并发、新框架）的价值，给出可证伪预判

> **最终标志**：学完这份计划后，拿掉专栏你仍能——看到任何一个并发工具/框架/新特性，说出它在「分工、同步、互斥」坐标系的哪个位置、解决什么问题、瓶颈在哪，并能预判它的适用场景和演化方向。

## 阶段一：逐层深入（~5 周）

### W1: 互斥与正确性——为什么并发程序会错（对应 01 模块后半 + 02-21）

- **假设**：所有并发 Bug 都能归因到可见性/原子性/有序性三类，且都能用"JMM 规则 + 互斥手段"定位到根因。
- **MECE 拆解**：
  - 子假设 1.1：可见性问题源于 CPU 缓存，volatile / synchronized / final 三类手段各覆盖一部分 → 验证方式：精读 01-01、01-02，写可见性复现 demo
  - 子假设 1.2：原子性问题源于线程切换，只能用互斥（锁）或 CAS 解决，volatile 解决不了 → 验证方式：精读 01-03、01-04、02-21（原子类）
  - 子假设 1.3：锁在解决正确性的同时引入死锁与性能两个新问题，且各有系统的应对方法论 → 验证方式：精读 01-05（死锁）、01-07（安全性/活跃性/性能）
- **动手验证**：
  1. 写一个 `long` 型共享变量的多线程累加程序，**故意复现**原子性丢失，再用 synchronized / AtomicLong 各修一遍；
  2. 写一个转账程序**故意制造死锁**，用 `jstack` 抓线程栈定位到死锁环，再按"破坏循环等待"修复；
  3. 用 JMH 跑一个小 benchmark：`synchronized` vs `ReentrantLock` vs `AtomicLong` 在高竞争下的吞吐量差异。
- **周末产出**：一篇 300-500 字的笔记《我用代码复现了三座大山》，附三个 demo 的关键代码和 jstack 截图。
- **DIKW 本周锚点**：数据 → 信息（从"听说过可见性"到"能讲清三个问题的因果链"）
- **失败日志**：本周必须记录 ≥1 条（比如：demo 没复现出预期 Bug，是不是 JIT 优化把代码干掉了？这本身就是一条关于"有序性"的真理解）

### W2: 同步与协作——管程这把万能钥匙（对应 01-06/01-08 + 02-14 ~ 02-19）

- **假设**：H2——所有协作工具底层都是 AQS 这一个管程变体。
- **MECE 拆解**：
  - 子假设 2.1：wait/notify 与 Lock/Condition 是同一管程模型的两种语法 → 验证方式：精读 01-06、02-14、02-15（Dubbo 异步转同步案例）
  - 子假设 2.2：Semaphore / CountDownLatch / CyclicBarrier 是管程在三种典型场景（限流/等待 N 个完成/对齐）的封装 → 验证方式：精读 02-16、02-19
  - 子假设 2.3：ReadWriteLock / StampedLock 是对"互斥粒度"的场景化优化，读多写少场景下乐观读能接近无锁性能 → 验证方式：精读 02-17、02-18
- **动手验证**：
  1. **手写一个阻塞队列**——先用 synchronized + wait/notify 写一版，再用 ReentrantLock + Condition 写一版，对比两版的代码结构（这一步直接验证子假设 2.1，也是理解 AQS 的最好热身）；
  2. 用 Semaphore 写一个连接池限流器，压测验证"最多 N 个并发"是否真的成立；
  3. 用 StampedLock 乐观读改造一个读多写少的缓存，JMH 对比 ReentrantReadWriteLock。
- **周末产出**：阻塞队列两版实现 + 一张"协作工具选型图"（场景 → 该用哪个工具 → 为什么）。
- **DIKW 本周锚点**：信息 → 知识（从"知道每个工具怎么用"到"知道它们为什么是同一样东西"）
- **失败日志**：本周必须记录 ≥1 条（比如：手写阻塞队列时 notify 漏了/用错 if 而不是 while——这就是管程语义的活教材）

### W3: 分工——线程池与异步编排（对应 01-09 ~ 01-12 + 02-20 ~ 02-27）

- **假设**：分工问题的本质是"任务粒度 × 线程成本"的匹配，线程池参数不是玄学而是可推导的。
- **MECE 拆解**：
  - 子假设 3.1：线程池的本质是生产者-消费者模式，七个参数里真正关键的是队列和拒绝策略 → 验证方式：精读 02-22，压测不同参数组合
  - 子假设 3.2：Future → CompletableFuture → CompletionService 是"异步结果协作"的三代演进，每一代解决上一代的具体痛点 → 验证方式：精读 02-23、02-24、02-25
  - 子假设 3.3：Fork/Join 只适用于"可递归分解的 CPU 密集型计算"，用错场景不如普通线程池 → 验证方式：精读 02-26，做对比实验
- **动手验证**：
  1. 用 CompletableFuture 实现专栏里的"烧水泡茶"最优编排，画出任务依赖 DAG；
  2. 给一个 IO 密集 + 一个 CPU 密集的 mock 服务各配一个线程池，用压测数据推导合理线程数（验证"线程数公式"在你的机器上成不成立）；
  3. 用 Fork/Join 并行归并排序，对比 `Arrays.parallelSort` 和单线程排序在不同数据规模下的耗时，找到"不值得并行"的临界点。
- **周末产出**：一张"烧水泡茶"DAG 图 + 一份线程池参数推导记录（含压测数据）。
- **DIKW 本周锚点**：知识层巩固（能对"这个场景该不该上线程池/上几个线程"给出有依据的判断）
- **失败日志**：本周必须记录 ≥1 条（线程池压测结果不符合预期时，记录你怀疑的变量和排查路径）

### W4: 模式与顶级实现——从"会用"到"看懂"（对应 03 模块全部 + 04 模块全部）

- **假设**：所有并发设计模式都是"消灭共享"或"规范分工"的不同招式；生产级框架的精妙之处都能用前三周的原理解释。
- **MECE 拆解**：
  - 子假设 4.1：Immutability / COW / ThreadLocal 三模式同属于"消灭共享变量"这一路 → 验证方式：精读 03-28、03-29、03-30，归纳共同前提
  - 子假设 4.2：Guarded Suspension / Balking / 两阶段终止是"规范线程行为"的模式，生产者-消费者 / Thread-Per-Message / Worker Thread 是"规范分工"的模式 → 验证方式：精读 03-31 ~ 03-36，每个模式写一个最小实现
  - 子假设 4.3：Netty / Disruptor / HiKariCP 的高性能都能归因到前三周学过的具体手段（无锁、消除伪共享、批量、分工）→ 验证方式：精读 04-38 ~ 04-41，逐个案例做"归因表"
- **动手验证**：
  1. 从 9 个模式里任选 3 个写最小可运行实现（推荐：生产者-消费者、两阶段终止、Immutability）；
  2. 读 Disruptor 的 RingBuffer 核心源码（或 HiKariCP 的 ConcurrentBag），写一份"它为什么快"的归因分析——每一条性能手段必须能对应到 W1-W3 的某个原理；
  3. 用 `System.identityHashCode` + 填充字段复现一次"伪共享"并修复，JMH 看差距。
- **周末产出**：一篇 800 字以上的源码归因分析《Disruptor（或 HiKariCP）为什么快》——这是全计划分量最重的产出。
- **DIKW 本周锚点**：知识 → 智慧过渡（开始看到"不同框架背后是相同的结构"）
- **失败日志**：本周必须记录 ≥1 条（读源码卡在哪、哪个概念回炉，都记下来）

### W5: 对岸与判断——跳出 JUC 看并发（对应 05 模块 + 材料外补充）

- **假设**：H3——虚拟线程只改变分工成本，不改变同步/互斥问题。
- **MECE 拆解**：
  - 子假设 5.1：Actor / CSP / STM 与管程是对同一问题的不同理论回答，差异在"共享内存 vs 消息传递"这个世界观分岔 → 验证方式：精读 05-42、05-43、05-45，做模型对比表
  - 子假设 5.2：协程/虚拟线程解决的是"线程太贵"的分工成本问题，对互斥和同步问题无能为力 → 验证方式：精读 05-44，补充读 JEP 444（Virtual Threads）与 JEP 453（Structured Concurrency）官方文档
  - 子假设 5.3：能预判"虚拟线程普及后哪些 JUC 工具会衰落、哪些会更重要" → 验证方式：基于 5.1/5.2 的结论外推，写下可证伪预判
- **动手验证**：
  1. 用 JDK 21+ 写一组对比实验：平台线程池 vs 虚拟线程跑 1 万个 IO 型任务，看吞吐与内存差异；
  2. 用虚拟线程 + synchronized 复现一次 pin（钉住）问题，观察载波线程被占用——这一步直接考验 H3；
  3. 用 Go（或 Kotlin 协程）写一个 CSP 风格的 ping-pong，体会"不要通过共享内存来通信"的世界观。
- **周末产出**：一篇判断文《虚拟线程会让 JUC 过时吗？——我的可证伪预判》，文中必须包含：① 你认为会衰落的 2 个工具 + 理由；② 你认为会更重要的 2 个工具 + 理由；③ 一个"如果发生 X 就说明我错了"的检验条件。
- **DIKW 本周锚点**：智慧层（能把 Java 的并发结构映射到 Go/Actor 的世界，看到相同问题域的不同解）
- **失败日志**：本周必须记录 ≥1 条
