> **领域类型**：T 型（技术/工程）为主，M 型（心智/思维）为辅——前四周在工程机制上做可验证的实验，最后收束到架构判断力。

## 学习前：写下你的初始假设

*写下日期：2026-08-09*

> 以下假设基于书的论点与你的结算场景生成。**开始前请写下你自己的版本——哪怕先抄，后面每周拿实验结果来改。**

H1: 可靠性的工程本质不是「消除失败」，而是「把不可靠节点的失败压缩到可检测、可恢复的窗口内」。所有方案——共识、事务、容错、冗余——都在「恢复窗口大小 × 实现成本」这个平面上做交易，没有例外。
   → 如果错了：发现某个主流方案真的消除了某类失败（而不是更快检测/更快恢复它）。

H2: 架构演进是单向的「复杂度下沉」：应用代码 → 框架类库 → 基础设施。每下沉一步，开发者就放弃一层定制权。判断一个新架构范式有没有前途，就看它下沉的东西是不是大家本来就不想管的——Spring Cloud 下沉注册发现成功了（没人想手写），ESB 统一编排失败了（业务逻辑没人愿意交出去）。
   → 如果错了：出现一个把复杂度从基础设施拿回应用层且大规模成功的案例。

H3: 结算/资金类系统的终局是「局部强一致（单库事务内）+ 全局最终一致（SAGA/对账）+ 事前幂等」，纯 XA/2PC 会退出在线交易链路，TCC 只在高价值、低并发、接口可控的链路划算。
   → 如果错了：你实际工作中看到 2PC/TCC 在结算核心链路成为主流方案且长期稳定运行。

## 阶段一：逐层深入（~5 周）

周序不按书序，按「对你判断力的杠杆大小」排：事务（你的本命）→ 共识（信任之根）→ 治理（稳定性工程）→ 基础设施（下沉最前沿）→ 合成（演进判断力 + 面试实战）。

### W1: 事务与一致性 —— 结算系统的本命问题

- **假设**：分布式事务没有银弹，所有方案都是一致性、可用性、性能、改造成本的四维权衡；选型的正确姿势是先定「哪些状态必须强一致」，再让其余状态走最终一致 + 对账兜底。
- **MECE 拆解**：
  - 子假设 1.1：CAP 不是「三选二」的菜单，是边界声明——分区必然发生时，你要在设计文档里提前写下「牺牲 C 还是 A」，而不是事后补救。 → 验证方式：找出你系统中一条真实链路，写下它在网络分区时的实际行为，再写下「应该是」的行为，对比差距
  - 子假设 1.2：TCC 的成本不在框架，在「业务接口三分化改造」——每个操作都要造出业务语义上的 Try/Confirm/Cancel 等价物，所以只有高价值、低并发、接口自控的链路才划算。 → 验证方式：拿「清分→结算→打款」三段式设计 TCC 版状态机，数出需要新增多少个补偿接口和状态字段
  - 子假设 1.3：SAGA 缺隔离性（中间态可被读到），所以必须配「对账稽核」兜底——对账不是 SAGA 的补丁，是最终一致性体系的正式组件。 → 验证方式：推演 SAGA 版结算在「第二个参与者成功、第三个失败」时的数据可见性，写出对账任务必须校验的不变量清单
- **动手验证**：同一结算场景（清分→结算→打款），分别用可靠事件队列、TCC、SAGA 写出状态机设计（纸面即可），推演每个中间态挂掉的恢复路径，产出三列决策矩阵：一致性保证 / 改造成本 / 失败恢复路径数。
- **面试转化**：把决策矩阵浓缩成「设计一个日终结算系统」的 45 分钟系统设计面试提纲。
- **周末产出**：《结算事务方案选型决策矩阵》+ 面试提纲。
- **DIKW 本周锚点**：数据 → 信息（能说清 CAP/TCC/SAGA 之间的取舍关系，而不是背定义）。
- **失败日志**（≥1 条）：
  ```
  * 时间：___  * 任务：___
  * 失败在哪一步：___
  * 原因：□理解错机制 □操作不到位 □前提不具备 □没拦住错误
  * 如果重来，我会：___
  ```

### W2: 共识与信任根 —— 注册中心为什么长这样

- **假设**：共识算法是所有「分布式协调设施」的信任根；理解它之后，注册中心、配置中心、分布式锁的选型争论都会自动变得清晰。
- **MECE 拆解**：
  - 子假设 2.1：Paxos/Raft 的关键不是流程，是不变量——「两阶段 + 多数派」保证已提交的值永不回滚。能讲清这个不变量 = 真懂，背流程 = 假懂。 → 验证方式：不看资料，向同事（或对着录音）讲清「为什么多数派相交就能防回滚」，卡壳处就是缺口
  - 子假设 2.2：注册中心要 AP、配置中心要 CP——因为路由错误可以重试自愈，配置错误是全局事故。这不是口味之争，是失败代价不对称。 → 验证方式：读 Nacos 的 AP/CP 双模设计文档，把它和这条假设对照，看是否吻合
  - 子假设 2.3：etcd vs ZooKeeper 之争本质是「为 K8s 生态定制」vs「通用协调原语」的生态位之争，不是性能之争。 → 验证方式：对比两者的 watch 机制与典型使用方（K8s 全部 / Kafka 老版本）
- **动手验证**：跑 raft 官方可视化动画推演一次 leader 选举与日志复制；本地起 etcd 3 节点集群，kill leader 观察重选举，再 kill 第二节点观察集群不可用时的读行为（验证多数派约束）。
- **面试转化**：面试高频题「设计一个注册中心」——写出提纲：存储模型、一致性选择、健康检查、推送 vs 轮询、容灾。
- **周末产出**：200 字讲清 Paxos 核心不变量 + 《注册中心选型论证》一页纸。
- **DIKW 本周锚点**：信息 → 知识（面对任何协调设施的选型争论，能从「失败代价对称性」切入判断）。
- **失败日志**（≥1 条）

### W3: 流量治理与可观测性 —— 稳定性工程的两大支柱

- **假设**：容错与限流的全部模式都可以从两个变量推出——「调用方等得起多久」和「重试有没有副作用」；可观测性里链路追踪是分布式特有的刚需，因为因果链跨进程断裂了。
- **MECE 拆解**：
  - 子假设 3.1：容错模式（failover/failfast/failsafe/failback/forking）的选型 = f(延迟预算, 重试副作用)。结算场景的重试必须幂等前置，否则容错变事故放大器。 → 验证方式：盘点你负责链路的重试配置，逐条检查「这个重试如果执行两次会怎样」
  - 子假设 3.2：限流算法（计数器/滑动窗口/漏桶/令牌桶）的唯一实质差异是突发吸收能力；选型先回答「我的系统能不能吸收突发」。 → 验证方式：用压测工具对 demo 接口分别配令牌桶和漏桶，观察突发流量下两者的放行曲线
  - 子假设 3.3：没有 trace 的分布式排障退化为猜——因为「请求经过了哪些服务、每段耗时多少」在跨进程后没有任何单点知道。 → 验证方式：注入一个人为延迟故障，先只用日志排查（体验痛苦），再用 trace 排查（对比定位速度）
- **动手验证**：在测试环境或 demo 系统注入延迟故障，严格执行「metrics 定方向 → trace 定服务 → log 定代码行」的排查顺序并计时；写一份《结算接口超时排障 playbook》。
- **面试转化**：面试题「线上接口超时怎么排查」——把 playbook 讲成有条理的五步答案。
- **周末产出**：排障 playbook（含真实注入实验的计时对比数据）。
- **DIKW 本周锚点**：信息 → 知识（能设计排障顺序，而不是只会用工具）。
- **失败日志**（≥1 条）

### W4: 不可变基础设施与服务网格 —— 下沉的最前沿

- **假设**：K8s 的本质是声明式收敛（reconciliation loop），服务网格的本质是把通信治理从进程内搬到进程外；而网格正在被自己引入的复杂度反噬——这是判断它未来走向的关键张力。
- **MECE 拆解**：
  - 子假设 4.1：理解 reconciliation loop 就理解了 K8s 全部设计——声明 desired state，控制器持续把 current state 收敛过去。自愈、滚动更新、HPA 全是这一个机制的实例。 → 验证方式：kill 一个 Pod 观察恢复；再关掉 controller-manager 后 kill Pod 观察恢复是否停止（验证「自愈来自控制器而非魔法」）
  - 子假设 4.2：sidecar 模式的三个代价（资源翻倍、运维面变宽、调试链路变长）正在被 ambient mesh / eBPF 修正——这是「下沉后的再优化」，方向是把代理也沉到节点级/内核级。 → 验证方式：对比 sidecar 模式与 ambient/eBPF 方案的资源占用与延迟数据（官方 benchmark 或实测）
  - 子假设 4.3：「Service Mesh 会不会成为下一个 ESB」是检验 H2 的最佳对仗题——两者都想统一通信基础设施，差异在于 ESB 想统一的是业务编排（没人愿意交），Mesh 统一的是通信治理（没人想要）。 → 验证方式：写一篇对仗分析，论点必须落到「统一的东西大家愿不愿意交出去」
- **动手验证**：minikube/kind 起集群，装 Istio（或 ambient 模式），完成一次金丝雀发布 + 一次 fault injection（5s 延迟 + 50% 500），观察流量切换与故障行为；画一张 reconciliation loop 图解。
- **面试转化**：面试题「谈谈你对云原生/服务网格的理解」——用「下沉」框架讲：每层下沉了什么、代价是什么、下一步往哪走。
- **周末产出**：《Mesh vs ESB 对仗分析》一篇 + reconciliation loop 图解一张。
- **DIKW 本周锚点**：知识 → 智慧（「谁愿意交出控制权」这个判据能迁移到任何技术治理问题）。
- **失败日志**（≥1 条，本周环境坑多，每条都值钱）

## 验收标准：学习结束时你能回答这 5 个问题

Q1: 从零设计一个日终结算系统：事务、幂等、对账各怎么选？每个选择的理由必须从原理出发（一致性需求 × 失败代价），而不是「我们公司就这么做」。
Q2: 明天出现一个宣称「取代 Istio、延迟降 80%」的新项目，你在决定投入精力前先查哪 3 个信息？（提示：它沉到了哪一层？代价转嫁给了谁？有没有违反你已知的边界？）
Q3: 生产故障：结算单卡在中间态、日志无异常。你按什么顺序、检查哪 5 个地方定位根因？
Q4: 初始假设 H1/H2/H3 现在还成立吗？每条用这 5 周的证据回答「成立 / 修正为___ / 被推翻」。
Q5: 给出一个可证伪的 2026–2028 预判：「我认为 ___ 会发生，因为下沉主线会推动 ___；如果 ___ 没有出现，就说明我错了。」
