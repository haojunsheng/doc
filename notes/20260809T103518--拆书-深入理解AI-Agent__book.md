- **x**：模型迭代飞快却仍不可靠，为什么有的 Agent 能替用户处理数周、涉钱、与真人反复交涉的长程任务，而多数 Agent 连"不无限循环"都做不到——Agent 的能力上限到底由什么决定？
- **f**：答案不是模型，是 Harness：Agent = LLM + 上下文 + 工具，眼睛（上下文）决定能力上限，可靠性来自围绕上下文与工具建立的约束、验证与纠正机制。机制底座是"上下文学习 = 检索而非推理"，一切工程化信息管理（状态栏、压缩、Skills）都在给模型补"提炼层"，而"交互"第三轴用外部观测喂入模型自己想不出的信息；再用评估闭环度量进步，把运行经验写回四种载体，形成持续进化。
- **f(x)**：优化 Agent 不再从"换更强的模型"开始，而是先审计"它看到什么、信息有没有被提炼、能不能核实"；任何改动之前先立评估基线；把"模型会错"当默认前提设计检测-恢复-终止路径，而不是事后打补丁。

# x：作者在讨论什么问题

同一个前沿模型，Pine 能靠它替用户打电话与运营商协商账单、与商家交涉退款、取消订阅——动辄几十轮交涉，任何一步出错都是真金白银的损失；而绝大多数 Agent 系统连"打了三次电话还继续打""任务做到一半忘了原始目标"这类基础故障都止不住。差异不在模型：模型能力正在商品化，同一代模型人人可用。那差异在哪？这是全书反复回到的疑问——**Agent 的能力上限到底由什么决定，可靠性是从哪里长出来的？**

旧默认答案是模型决定论：等更强的模型，Agent 自然变好。但第一章的消融实验给出了反证——去掉上下文组件、工具结果或系统提示词中的任何一块，系统都会显著退化；同一个模型，换个 Harness，任务准确率能从 52.8% 跳到 66.5%（后记引用的实验）。模型没动，结果变了。问题成立：可靠性来自模型之外。

# f：作者怎样回答

作者的公式：**Agent = LLM + 上下文 + 工具**，对应大脑 + 眼睛 + 手脚（学术层为策略、观察空间、动作空间）。三者缺一不可，但分量不等——**眼睛是决定性的**。回答由三块咬合成一台机器：

**第一块，机制底座：上下文学习 = 检索而非推理。** 注意力擅长在已有内容里"查找"（笼子 37 里是什么猫），不擅长主动"归纳统计"（100 个笼子里有多少只黑猫）——后者要么靠思维链现算，要么算错。因此上下文窗口是一台"只有一半的检索引擎"，缺的是提炼层。整本第二章都是围绕"补提炼层"展开的工程：状态栏把散在轨迹里的隐式状态用代码提前算成键值对**加**进上下文（弱模型补准确率、强模型省一个数量级的思考量），压缩把臃肿的原始记录**换**成提炼结论，Skills 按需加载、KV Cache 布局保住前缀。更深的发现是"交互"这条第三轴：想得更久、试得更多都只在模型自己的脑子里打转，变不出上下文里没有的信息；只有让外部的"仪器"观测真实世界（测试过没过、按钮有没有跑出屏幕、电话到底打了几次）再把观测写回，才能突破——状态栏把"闭卷考试"变成"随时查一眼真实世界"，循环工程的瓶颈在验证器而不在模型，第十章判断多 Agent 是否优于单 Agent 的唯一准则也是"是否引入了生成时不存在的新信息"。这条轴贯穿全书。

**第二块，手脚与元能力：工具 + 代码。** 工具设计决定 Agent 能做什么，五类工具各有安全与保真原则（模型感知到的世界与工具操作的世界不能有系统性偏差）；而 Coding Agent + 文件系统是所有通用 Agent 最核心的基础——代码是"元能力"：既完成任务，又积累知识、创造工具、优化自身。关键洞察：Coding Agent 成熟不是代码模型强，而是软件工程几十年攒下的测试套件、类型系统、版本控制天然构成了一套强大的 Harness；Agent 的可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应的检测、恢复与终止路径。

**第三块，度量与进化：评估闭环。** "没有评估，就没有进步"——观察→假设→实验→验证，把 Agent 工程从经验炼金术变成科学工程。运行经验不随会话消散：按知识文档、Prompt、Skills、程序、模型参数四种载体，在线执行与离线学习分离，生成可验证、可回滚的候选更新（第八、七章）。"SFT 记忆、RL 泛化""数据和环境比算法更重要"是参数层的两条主线。

三块的关系：第一块回答"模型为何不可靠、靠什么补偿"，第二块回答"凭什么让它可靠行动"，第三块回答"怎么知道它真的变好了、怎样让它长期变好"。后记把这台机器拧成一条飞轮：用户提出真实难题，Harness 把模型暂时做不好的事补上，补救沉淀成下一轮训练信号，模型内化一层能力，对应 Harness 层就删掉一层——模型会一层层吃掉 Harness，但永远吃不完（训练以月计，业务等不起；真实约束无法全部内化；每代模型都打开新的前沿，前沿处最不稳）。所以"好的设计原则穿越模型的迭代周期"。

```

   有的连"不无限循环"都做不到？
        │
        ▼
f: 能力上限 = 眼睛(上下文) × 手脚(工具) × 验证(评估)
   ┌─────────────────────────────────┐
   │ 构建: 显式信息管理                │
   │  检索≠推理 → 补提炼层(状态栏/压缩) │──→ 评估: 没有评估就没有进步
   │  交互第三轴: 外部观测写回          │        │

        │ 写回
        └────────── 飞轮 ──────────┘ (模型内化一层 → Harness 删一层)
```

# f(x)：怎样回应这个世界

接受 f 之后，处理 Agent 问题的顺序、标准和提问方式都变了。

判断变了：不再问"哪个模型最强"，先问"它看到什么、看到的内容是否已被提炼成可直接检索的知识、每条关键信息能否被外部观测核实"。模型升级带来的不是惊喜而是检查单——新模型内化了哪层约束，对应的 Harness 层就可以拆掉；旧瓶颈若还在，说明它还没走到那一步。

行动顺序变了：任何一次优化之前，先立评估基线——没有基线，"变好"只是感觉。然后先动上下文与工具（信息怎么组织、故障有没有路径），再考虑换模型。工具不可靠时的处理也定了形：状态栏必须用代码维护而非让 LLM 批量统计；状态栏的信息只来自真实观测，否则"仪器"会读出错的刻度；压缩删除原文前先确认提炼覆盖了所有会被问的问题——这些都是 f 直接推出的操作纪律。

提问变了：拿到一条 Agent 指令或一段上下文，"这条信息模型自己想不想得出来？"成为默认检查项——想得出来的只是替它省力，想不出来的（真实时间、执行结果、系统状态）才值得注入。这是书里"仪器 vs 算盘"的分界。

克制也变了：不再追着业界名词跑。"实践在前，命名在后"——名词流行时头部公司早已把坑趟完。与其等名词，不如让自己的业务把 Harness 逼出来；而应用层真正的护城河在技术之外（数据、渠道、信任），Harness 只用来争取时间。最后，对"模型会不会吃掉 Harness"的焦虑被拆解为一条可操作的预期：会吃，但一层一层、永远吃不完——站在飞轮两端中的任何一端，工作都清晰可见。
