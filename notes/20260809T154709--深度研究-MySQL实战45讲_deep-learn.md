## 阶段一：逐层深入（六周）

### W1 · 索引：数据的组织方式决定一切查询的上限（笔记 04、05、09、10、11）

- **本周假设**：一张表的性能天花板在建表时就定了——因为"每张表就是若干棵 B+ 树，主键树叶子存整行，二级索引树叶子存主键"，所有查询优化都是在这个结构约束下少扫树、少回表。
- **MECE 拆解**（B+ 树被利用的四种方式 + 一个失灵场景，不重不漏）：
  - 子假设 1.1 **等值定位**：有序性支持 O(logN) 树搜索 → 验证：手绘 B+ 树，标出 `WHERE id=5` 的搜索路径
  - 子假设 1.2 **范围扫描**：叶子链表支持范围 → 验证：`WHERE id BETWEEN`，对比走索引与全表扫的 `EXPLAIN rows`
  - 子假设 1.3 **覆盖/下推**：不回表（覆盖索引）与少回表（ICP 索引条件下推、MRR）是独立的优化维度 → 验证：构造三种查询，观察 `Extra` 列 `Using index` / `Using index condition` 的差异
  - 子假设 1.4 **写入侧代价**：普通索引写快靠 change buffer，唯一索引不能用 change buffer——所以"普通索引 vs 唯一索引"的答案是业务约束优先、性能差异只在写密集型场景显著 → 验证：两张结构相同的表，change buffer 开关对比批量插入 TPS
  - 子假设 1.5 **优化器失灵**：选错索引的根因是采样统计偏差 + cost 模型对"扫描行数 × 回表代价"的误判 → 验证：复现第 10 讲案例，`ANALYZE TABLE` 前后对比执行计划
- **动手实验**：
  1. 建 10 万行表，分别执行主键查询 / 二级索引+回表 / 覆盖索引，`EXPLAIN` + 计时三对照
  2. 第 11 讲前缀索引实验：`SELECT COUNT(DISTINCT LEFT(email,N))/COUNT(*)` 扫描 N=4..8，画出区分度曲线，亲手确定前缀长度
- **对话能力验收**（能脱稿回答才算过）：
  - Q："为什么建索引能加速？" —— 答不出"B+ 树有序性 + 叶子链表"这一层，只在"目录"比喻层的，不合格
  - Q："唯一索引和普通索引怎么选？" —— 必须答出 change buffer 对普通索引的写优化 + "查询性能差异可忽略"的定量理由
  - Q："字符串字段怎么加索引？" —— 必须能给出前缀索引 vs 倒序存储 vs hash 字段三种方案及各自适用场景
- **周末产出**：「索引决策卡」一张——输入一条慢 SQL + 表结构，输出建索引方案的推理链
- **DIKW 锚点**：信息→知识（看到 `EXPLAIN` 输出能反推出 B+ 树上发生了什么）

### W2 · 事务与 MVCC：可见性是一套确定性规则（笔记 03 回顾、08、20）

- **本周假设**：MVCC 不是"保存了多个版本"这句废话——它是「undo log 版本链 + read-view 活跃事务数组」的可见性判定算法；RR 和 RC 的全部差异只在 read-view 的创建时机（事务首次快照读 vs 每条语句）。
- **MECE 拆解**：
  - 子假设 2.1：版本链由 trx_id + roll_pointer 构成，可见性判断可手工模拟 → 验证：把第 08 讲事务 A/B/C 例子画成版本链，手工执行可见性算法，预测 k 值
  - 子假设 2.2：**快照读与当前读是两套规则**——事务 A 快照读看到 k=1、事务 B 当前读看到 k=3，这不矛盾，是 read-view 只对快照读生效 → 验证：双 session 复现第 08 讲图 1 的完整时序
  - 子假设 2.3：幻读是"当前读两次范围查询结果不一致"，RR 下由 next-key lock 防住——但这只在加锁读路径成立，纯快照读防不住 → 验证：第 20 讲场景，分别用裸 `SELECT` 和 `SELECT ... FOR UPDATE` 观察幻读是否出现
- **动手实验**：双 session 严格按课程时序操作；每步先用规则预测结果再执行，**预测错一次 = 记一条失败日志**（这是本周最重要的练习方式）
- **对话能力验收**：
  - Q："RR 和 RC 区别？" —— 只答"可重复读"四个字的淘汰；必须落到 read-view 创建时机 + 各举一个业务场景（对账用 RR 的一致性快照）
  - Q："MySQL 的 RR 有没有幻读？" —— 合格答案必须区分快照读/当前读两条路径，而不是背"解决了/没解决"
- **周末产出**：200 字费曼讲解「为什么同一个时刻，两个事务查同一张表结果不同」，讲给非 MySQL 同事
- **DIKW 锚点**：信息→知识（任意事务时序 → 独立推出各事务看到什么）
- **失败日志**：≥1 条（本周预测-验证法天然产日志）

### W3 · 锁：两原则、两优化、一 bug（笔记 06、07、21、30、32、40）

- **本周假设**：InnoDB 加锁行为 100% 可被第 21 讲的规则集预测：**原则 1** 基本单位是 next-key lock（前开后闭）；**原则 2** 只锁访问到的对象；**优化 1** 唯一索引等值退化为行锁；**优化 2** 等值查询右边界不满足退化为间隙锁；**bug** 唯一索引范围查询访问到第一个不满足的值为止。锁问题从"玄学"变成"查表推理"。
- **MECE 拆解**（按锁的作用域分层，互斥且穷尽）：
  - 子假设 3.1 **全局/表层**：FTWRL 与 MDL 的阻塞面不同——DDL 被 MDL 卡住会雪崩（后续所有查询排队）→ 验证：长事务中执行 `ALTER TABLE`，观察第三个 session 的查询是否被堵
  - 子假设 3.2 **行层**：两阶段锁（执行时加、提交时放）→ 热点行是死锁和排队根源 → 验证：复现第 07 讲案例，理解"把热点行更新放到事务最后"为什么有效
  - 子假设 3.3 **间隙层**：无索引字段 `FOR UPDATE` = 锁全表全部间隙 → 验证：第 21 讲案例一，session B 插 id=8 阻塞、session C 改 id=10 成功
  - 子假设 3.4 **死锁层**：死锁检测 O(n²)，高并发下 CPU 打满可能来自检测本身 → 验证：构造死锁，逐行解读 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`；讨论 `innodb_deadlock_detect=off` + 超时的替代方案适用条件
- **动手实验**：第 21 讲全部案例逐个复现（课程明确警告"有些例子毁三观，建议亲手实践"）；8.0 用 `performance_schema.data_locks` 实际查看锁范围，与规则预测对照
- **对话能力验收**：
  - Q："我只改一行，为什么锁这么多？" —— 必须现场推出加锁区间（含退化判断）
  - Q："线上 DDL 把库搞挂了，可能是什么机制？" —— 必须答出 MDL 排队雪崩链
  - 结合你的结算背景自问：热点账户并发入账的扣减更新，锁怎么设计？（答案：单行 UPDATE 原子性 + 事务内热点操作靠后）
- **周末产出**：「加锁推理一页纸」——给定表结构 + SQL，五步推出锁范围
- **DIKW 锚点**：信息→知识
- **失败日志**：≥1 条

### W4 · 优化器与执行：逻辑相同 ≠ 执行路径相同（笔记 10 回顾、12、13、14、16、17、18、19、22、33）

- **本周假设**：所有"逻辑相同性能迥异"的 SQL，差异都在执行路径的三个变量上——**是否利用有序性**（函数/隐式转换破坏它）、**扫描多少行**（驱动表选择、LIMIT 深分页）、**中间结果放哪**（sort_buffer / 内存临时表 vs 磁盘临时表）。
- **MECE 拆解**：
  - 子假设 4.1 **有序性破坏**：`month(t_modified)=7` 用不上树搜索不是"MySQL 规定"，是函数结果破坏了键值有序性（第 18 讲）；隐式类型转换、字符集不一致同理 → 验证：复现第 18 讲三个案例并各自改写
  - 子假设 4.2 **排序路径**：全字段排序 vs rowid 排序由 `max_length_for_sort_data` 决定，filesort 不一定是坏事、内存放不下才危险 → 验证：第 16 讲 `OPTIMIZER_TRACE` 跟踪 order by 全过程
  - 子假设 4.3 **扫描放大**：`LIMIT 1000,20` 慢在丢弃前 1000 行；`COUNT(*)` 慢在 InnoDB 必须遍历（MyISAM 存了计数）→ 验证：延迟关联改写分页；14 讲的 count 方案对比
  - 子假设 4.4 **抖动与资源**：刷脏页（redo log 满 / buffer pool 脏页比例）导致"抖一下"；大查询打爆内存的担心由 `max_execution_time` 与全表扫描的 buffer pool 污染机制回答 → 验证：第 12 讲 flush 参数实验；33 讲大查询观察 buffer pool
- **动手实验**：第 18 讲三案例必做；`SET optimizer_trace="enabled=on"` 完整走一遍 order by 分析
- **对话能力验收**：

### W5 · 日志、复制与高可用：不丢数据 vs 快速恢复的取舍学（笔记 02 回顾、23-29、31）

- **本周假设**（H3 的展开）：两阶段提交保证 crash-safe；binlog 三种格式在"主备一致性 vs 日志体积"间取舍；备库延迟的架构根因是 sql_thread 单线程 vs 主库并发写入的结构性不匹配，所以解法只能是并行复制；而所有并行策略都必须满足两条铁律——**同一行的事务分发到同一 worker（防覆盖）、同一事务不拆分（防中间态可见）**。
- **MECE 拆解**：
  - 子假设 5.1 **不丢**：双 1 配置（`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`）才等于"提交即不丢"，每组都是性能与安全的 trade-off → 验证：sysbench 对比双 1 与非双 1 的 TPS
  - 子假设 5.2 **一致**：statement 格式的 `DELETE ... LIMIT` 主备可能不一致，row 格式以体积换确定性 → 验证：`mysqlbinlog` 解析同一事务三种格式
  - 子假设 5.3 **追平**：5.6 库级并行 → 5.7 组提交并行（LOGICAL_CLOCK）→ 8.0 writeset 的演进主线是"在两条铁律下扩大可并行的事务集合" → 验证：复述第 26 讲按表/按行/组提交三种策略各自如何满足两条铁律
  - 子假设 5.4 **切换**：MHA/主从切换的可靠性取决于位点同步与 `readonly` 时序；读写分离的"过期读"由 `seconds_behind_master` 判断或强制走主方案解决 → 验证：Docker 一主一从，kill 主库演练切换，记录位点
- **动手实验**：Docker 一主一从搭建（本周核心动手项）；sysbench 持续写入时观察 `Seconds_Behind_Master`；并行复制参数开关对比追平速度
- **对话能力验收**：
  - Q："备库延迟几小时，加机器有用吗？" —— 必须答出"单线程 replay 是架构瓶颈，并行复制才是正解"+ 两条分发铁律
  - Q："你们的读写分离怎么避免读到旧数据？" —— 必须给出至少两种方案（强制走主/半同步+位点等待/GTID 等待）及代价
- **周末产出**：「高可用方案取舍表」——异步/半同步/MGR 三列，行是 RPO、RTO、性能损耗、运维复杂度

### W6 · 工程边界：面试不常考、生产一定会遇到（笔记 34-45、15、44）

- **本周假设**：这一组"杂题"共享同一条暗线——**每个诡异现象都是某个实现细节在边界条件下的暴露**：自增 ID 不连续（回滚不退、批量预留）、KILL 不掉（kill 只是标记，等检查点）、临时表重名（session 级命名空间）、内存引擎表重启丢数据但不锁全表的原因……把现象翻译回机制，就不需要背任何一条。
- **MECE 拆解**（按机制域归组）：
  - 子假设 6.1 **JOIN 族**（34、35）：能不能用 JOIN = 驱动表选择 + 被驱动表有无索引；BNL→BKA 的优化链是"join buffer + MRR 把随机回表变顺序" → 验证：100 行 × 10 万行两表，有/无索引四组合对比
  - 子假设 6.2 **临时表族**（36、37）：内存临时表转磁盘由 `tmp_table_size` 触发；union/group by distinct 的临时表使用可预测 → 验证：观察 `Created_tmp_disk_tables`
  - 子假设 6.3 **自增与插入族**（39、40、45）：自增不连续的三个原因；insert 的锁（唯一键冲突检测时的 next-key lock）；自增用完的溢出行为 → 验证：回滚 + 批量插入观察跳跃
  - 子假设 6.4 **引擎与分区族**（38、43、41、42）：Memory 引擎的适用边界；分区表的本质是"多个物理表一个逻辑表"；最快复制表的方法是导出导入还是 rename？→ 验证：41 讲三种复制表方法计时对比
- **动手实验**：JOIN 四组合对比（必做）；自增 ID 跳跃复现
- **对话能力验收**：
  - Q："DBA 不让用 JOIN，你怎么看？" —— 必须能说出"问题不在 JOIN 在无索引的被驱动表 + 驱动表选错"，并给出判定方法（这是第 34 讲开篇的真实生产争议）
