# 数据结构与算法 深度认知学习计划

> **领域类型**：T 型（技术/工程）——每个知识点都有可运行、可对拍、可证伪的代码实现，对错分明
> **目标深度**：C. 能判断——遇到陌生算法题能独立拆解建模，对工程选型（跳表 vs B+树、快排 vs 堆排）能给出有依据的判断
> **时间跨度**：约 6 周（冲刺模式，12h+/周）
> **最终标志**：学完这份计划后，给你一道没见过的 LeetCode Medium/Hard，你能在 5 分钟内说出它属于哪类模型、该用什么数据结构、复杂度边界在哪、为什么不能更优——即使还没写出代码

## 阶段一：逐层深入（~5 周）

> 冲刺模式裁剪说明：依据手册 + H2 假设，**跳过**红黑树实现细节（25/26 讲只看思想）、BM/KMP/AC 自动机（32-34、36 讲只懂原理）、拓扑排序/最短路径/A*（43/44/49 讲只懂场景）、概率统计/向量空间/并行算法（46/47/51 讲选读）。省下的约 8 讲时间全部投给动态规划和链表/树的边界训练。

### W1: 复杂度心法 + 线性结构三连（数组 / 链表 / 栈队列）

- **假设**：数组 vs 链表的本质差异是"随机访问 vs 动态扩容"的物理布局差异，一切操作复杂度差异都由此推导，不需要背
- **MECE 拆解**：
  - 子假设 1.1：复杂度分析能脱离具体代码，只看循环/递归结构就给出大 O → 验证方式：不看专栏分析，独立分析 05-09 讲所有代码片段的复杂度，再对照原文找差异
  - 子假设 1.2：链表题的错误 90% 出在边界（空表、单节点、头尾、环），不在主逻辑 → 验证方式：手写 LRU 缓存（06 讲）、链表反转、求中间节点、环检测，统计自己的 bug 分布
  - 子假设 1.3：栈和队列的价值在"约束即表达力"——限制操作反而能建模一类问题（浏览器前进后退、线程池排队）→ 验证方式：用两个栈实现队列、用栈实现浏览器前进后退（08/09 讲思考题）
- **动手验证**：Java 实现动态数组（支持扩容）、单链表全套操作、链式栈、循环队列；每题先默写再对拍专栏代码
- **周末产出**：一张"数组 vs 链表全操作复杂度对照图"（含缓存局部性这一隐藏维度）+ 一段 200 字讲解"为什么 Redis 的 list 早期用 ziplist 而不是链表"
- **DIKW 本周锚点**：数据 → 信息（能把每个操作和它的复杂度用"物理布局"这条逻辑串起来）
- **失败日志**：本周必须记录 ≥1 条（链表边界 bug 是最好的素材）

### W2: 递归 + 排序 + 二分查找（分治思想的第一次显形）

- **假设**：递归不是语法是思维——"把问题分解为同构子问题"是后续分治、回溯、DP 的共同母题；排序和二分是它的两个最纯粹的应用
- **MECE 拆解**：
  - 子假设 2.1：写出正确递归的关键是"递推公式 + 终止条件"两要素，而不是在脑子里模拟调用栈 → 验证方式：用两要素法手写归并排序、快排、二叉树遍历，禁止单步调试
  - 子假设 2.2：快排平均 O(nlogn) 但工程排序函数（如 Java Arrays.sort）用双轴快排+插入排序混合，因为常数因子和小数据场景主导真实性能 → 验证方式：读 14 讲， benchmark 自己实现的快排 vs 插入排序在 n=100/10⁴/10⁶ 下的表现
  - 子假设 2.3：二分查找的真正难点是变体（第一个等于、最后一个等于、第一个大于等于），不在基础版 → 验证方式：无 bug 写出 4 种变体 + 旋转数组搜索（Hot 100 原题）
- **动手验证**：递归树法分析归并/快排复杂度（27 讲）；用快排 partition 思想实现 O(n) 找第 K 大（12 讲）
- **周末产出**：一张"递归 → 分治 → 排序家族"演化图 + LeetCode Hot 100 二分专题 5 题 AC 记录
- **DIKW 本周锚点**：信息 → 知识（见到"有序"二字能条件反射想到二分，见到"第 K 大"想到 partition 或堆）
- **失败日志**：记录二分边界（mid 取上取中取下、while 条件）写错的至少 1 次

### W3: 哈希 + 树族（散列表 / 二叉树 / 堆 / 跳表 / Trie）

- **假设**：树族结构的全部分支都是在回答同一个问题——"如何在动态数据上同时保住查找和有序性"；散列表放弃了有序换 O(1)，树保住了有序付出 O(logn)
- **MECE 拆解**：
  - 子假设 3.1：工业级散列表的设计核心是冲突策略 + 扩容策略的权衡（拉链法 vs 开放寻址不是优劣是场景）→ 验证方式：手写拉链法散列表（含动态扩容），读 19 讲对照工业级还差什么
  - 子假设 3.2：二叉树面试题 = 遍历框架的变形（前中后序 + 层序四个模板能覆盖 Hot 100 全部树题）→ 验证方式：用四个模板套 Hot 100 树专题，统计覆盖率
  - 子假设 3.3：堆的价值不在排序而在"动态数据流上的 Top-K / 中位数"——堆排序反而不如快排（28 讲的标题就是线索）→ 验证方式：实现堆 + 用它解"数据流中位数"（Hot 100 Hard），并解释 28 讲"为什么堆排序没有快排快"（缓存局部性）
  - 子假设 3.4：跳表是"用空间换有序性的概率化妥协"，Redis 选它而非红黑树是实现复杂度与范围查询友好的权衡 → 验证方式：读 17、52 讲，写 200 字论证"如果让你设计 Redis zset 你选什么"
- **动手验证**：散列表（拉链法）、二叉树四种遍历模板、堆及堆排序；读 24 讲回答"有了散列表为什么还需要二叉树"
- **周末产出**：一张"散列表 vs 跳表 vs 红黑树 vs B+树 选型决策树"（这是 C 级深度的核心产物）+ Hot 100 哈希专题 5 题
- **DIKW 本周锚点**：知识层加固（能对 W3 决策树上的每个分支说出场景约束）
- **失败日志**：堆的 siftUp/siftDown 边界、散列表扩容时的 rehash 顺序，至少记录 1 条

### W4: 字符串匹配 + 图基础（按冲刺权重压缩的一周）

- **假设**：字符串匹配和图在 L8/P7 面试中是"知道存在 + 会说场景"即可的领域，真正可考的只有 Trie 和 BFS/DFS 两个点
- **MECE 拆解**：
  - 子假设 4.1：BF/RK 的价值是展示"哈希如何加速匹配"这一思想，KMP/BM 只需能讲清"坏字符/好后缀在利用已匹配信息跳过无效比较" → 验证方式：实现 BF 和 RK；对 KMP 只要求画出 next 数组的含义（32-34 讲）
  - 子假设 4.2：Trie 的考点是"前缀"场景识别（搜索提示、IP 路由、敏感词），不是实现 → 验证方式：读 35 讲 + 实现 Trie 基础版，说出它和散列表存字符串的本质差异
  - 子假设 4.3：图的 BFS/DFS 是所有图算法的母模板，三度好友、拓扑排序、最短路径都是模板+状态的组合 → 验证方式：邻接表建图 + 手写 BFS/DFS，用 BFS 解"三度好友"（31 讲）和 LeetCode 课程表（拓扑排序裸题）
- **动手验证**：BF/RK 代码、Trie 插入与前缀查询、图的邻接表表示 + BFS/DFS
- **周末产出**：一段 200 字讲解"敏感词过滤从 BF 到 AC 自动机的演化逻辑"（讲清演化 = 讲清每个算法在补前者的什么短板）+ Hot 100 图/BFS 专题 3 题
- **DIKW 本周锚点**：信息 → 知识（能把"算法演化史"讲成"短板修补史"，这是 Know-how 的标志）
- **失败日志**：Trie 节点设计（数组 vs 哈希表存子节点）的取舍纠结，记录 1 条

### W5: 四种算法思想（贪心 / 分治 / 回溯 / 动态规划）——本计划的主战场

- **假设**：四者是一条光谱而非四个孤岛——贪心是"每步最优且无需回头"，回溯是"穷举+剪枝"，DP 是"有重复子问题的回溯 + 状态表"，分治是"子问题不重叠的递归"；DP 最难是因为状态定义没有机械流程
- **MECE 拆解**：
  - 子假设 5.1：贪心题的关键不是代码而是"证明局部最优能推出全局最优"，证明不了就该换 DP → 验证方式：Huffman 编码（37 讲）+ LeetCode 跳跃游戏，写出贪心正确性的交换论证
  - 子假设 5.2：回溯 = DFS + 剪枝，八皇后和 0-1 背包是同一个骨架 → 验证方式：手写八皇后、全排列、子集，抽象出自己的回溯模板（选择列表/路径/撤销选择）
  - 子假设 5.3：DP 的三要素（最优子结构、无后效性、重复子问题）中，"状态定义"是唯一真正难的部分，且可通过"回溯记忆化 → 递推"的路径机械推出 → 验证方式：对凑单问题（40 讲）、编辑距离（42 讲）、股票买卖系列，每题都先写记忆化搜索再改递推，对比两者思维难度
  - 子假设 5.4：DP 能达到 Medium 稳定 AC、Hard 有思路，即满足 P7 面试要求（手册原话：掌握标志就是 LeetCode Medium）→ 验证方式：Hot 100 DP 专题 10 题，统计一次 AC 率
- **动手验证**：四思想各实现 2 个代表问题；全部 DP 题走"回溯 → 记忆化 → 递推"三步路径，禁止直接看题解
- **周末产出**：一张"四种算法思想光谱图"（横轴：子问题重叠程度，纵轴：是否需要全局最优证明）+ DP 专题 AC 统计 + 一段 200 字"为什么 DP 的状态定义难"（用自己的失败日志做论据）
- **DIKW 本周锚点**：知识 → 智慧的门槛（见到新题能先问"子问题重叠吗？需要证明贪心吗？"——这是跨题迁移的结构识别）
- **失败日志**：DP 状态定义想错的至少 2 条，这是本周最有价值的材料

### W6: 工程实战收束 + 螺旋回归（52-56 讲 + 假设复盘）

- **假设**：算法思想的工程价值在"选型权衡"而非"手写实现"——Redis、搜索引擎、Disruptor、限流器、短网址五个案例能覆盖全部 20 个知识点的应用场景
- **MECE 拆解**：
  - 子假设 6.1：五个实战案例的每个选型都能用"场景约束 → 复杂度要求 → 结构特性"的三段论复现 → 验证方式：读 52-56 讲前先自己推演选型，再对照王争的答案，记录分歧点
  - 子假设 6.2：H1-H3 三个初始假设此刻可以全部证伪或证实 → 验证方式：逐条回顾，写复盘
  - 子假设 6.3：短网址系统（56 讲）是微型系统设计题，能串起哈希、分布式 ID、存储选型——这是 P7 面试"算法+系统设计"结合点的预演 → 验证方式：独立画出短网址系统架构图，标注每个组件背后的数据结构

- **周末产出**：修订版知识结构图（对比阶段零那张，差异就是你的认知增量）+ 初始假设复盘文（≥500 字）
- **DIKW 本周锚点**：智慧层检验（能否把"约束 → 权衡 → 选型"这个结构迁移到结算系统的技术选型上——比如规则引擎为什么用 Aviator 表达式树）
