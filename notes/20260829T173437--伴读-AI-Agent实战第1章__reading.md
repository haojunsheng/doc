# 全局地图

## 一句话摘要

第1章是全书的地图：用「Agent = LLM + 上下文 + 工具」锚定 Agent 的本质，再把它在生产语境下展开成「Agent = Model + Harness」，核心论断是——模型能力正在商品化，真正的竞争力在模型之外的 Harness 工程（约束 / 验证 / 纠正）。

# 逐段伴读记录

## 第 1 段：公式与边界（L11-29）

### 结构标注

作者开篇加粗强调两个限定：「+」是工程组合、不是 RL 形式化定义；公式只描述 Agent 边界之内、**不包含 Environment**。

### 注疏（对手光）

作者在第一段就钉死「不包含 Environment」，不是技术细节，是论证策略：Harness 是「Agent 边界内、模型之外」（L279）、护栏执行层复核必须「上下文之外」（L476）、「物理部署位置不能决定概念归属」（L279）——全书关键命题都压在这条线上。但作者一边把 Environment 推出边界，一边又承认沙箱的「权限与重置机制」算 Harness、「沙箱内随行动变化的文件和进程」算 Environment，一条线同时穿过同一个沙箱。

### 碰撞记录

- 提问：这条「Agent / Environment 边界」是实线还是虚线——画在哪取决于你此刻想把哪部分算作「我要治理的对象」？
- 读者未正面回答此问，转向指定「工程范式演进」一节。

## 第 2 段：从提示工程到 Loop 工程：工程范式的演进（L321-339）

### 结构标注

本节三个动作：铺弧线（提示→上下文→Harness→Loop→Graph）、下论断（层层包含、子集关系、扩展工程师的关注范围和影响力）、给例证（LangChain Terminal Bench 52.8%→66.5%，改的是 Harness 不是模型）。

### 注疏（对手光）

「层层包含」是描述还是规定？真实造词史里，五个词是一群在不同实践问题上**几乎平行**的人各自起的名字（调 prompt 的人、撞上上下文窗口稀缺的人、发现治理代码是核心的人、做长程自治的人、做确定性编排的人），他们起名时脑子里没有「我在上一个词的子集里」的意识。作者把它们排成严格嵌套谱系，是事后诸葛亮的编年史。

### 碰撞记录

- 我的判断（当靶子）：提示→上下文→Harness 是真递进（每一步对应一个不解决就干不下去的问题）；Harness→Loop→Graph 存疑——作者说 Harness 已管「验证、纠正」，Loop 的「何时验证、何时完成」到底新增了什么？Graph 说「单个 Agent 循环正是执行图中的一个节点」，是不是只是把 Loop 画成了图？
- 读者反问：根本没有递进关系吗？里面也没有内在逻辑吗？
- 我的修正：有递进、有内在逻辑，但我上一轮打偏了——打的是修辞（层层包含），不是逻辑本身。真正的逻辑是四个「被迫的跃迁」：
  - 提示→上下文：视野从「一句话」扩到「模型能看到的一切」（逼因：prompt 再精也是一段话）
  - 上下文→Harness：性质从「管理信息」变成「治理行为」（逼因：信息够了照样幻觉/选错/死循环）
  - Harness→Loop：时间从「跑一次」延到「持续跑」（逼因：没人决定下一件该做什么）
  - Loop→Graph：结构从「一个循环」显式化成「一张图 + 持久化状态」（逼因：单循环装不下混合系统）
- 但「子集」是错的：真实关系不是「上一步全有、还多一点」，而是「上一步的注意力中心被移开」。上下文工程不是「更好的提示工程」，是「发现提示只是上下文一小块，于是不再盯着提示」。
- 用读者二分法重读：这套谱系本质是从**补丁层向语义层的迁移**，分水岭在 Harness——提示工程几乎全是补丁层（few-shot、CoT、格式修复都会被内化，书 L408 自认）；上下文工程一半补丁一半语义；Harness 的约束/验证/纠正依赖「外部审视」这个结构（模型无法自审），是语义层，吃不掉；Loop/Graph 是语义层在时间轴和结构轴上的深化。
- 收口：同一谱系两种读法——作者的「胜利叙事」（每层扩展工程师的影响力和掌控范围）vs「撤退叙事」（每层都是上一层失效后的撤退）。两种读法取决于你站在「模型会持续变强」还是「模型会长期卡在某个能力边界」哪一边。

### 旁逸：读者提出五问方法论（已保存至用户级记忆）

当作者提出一个新概念/方法时，先别急着接受，按五个问题拆一遍：
1. 它产生之前有哪些问题（前置问题 / 背景）
2. 它解决了哪些问题
3. 它解决不了哪些问题（边界 / 局限）
4. 它会不会引入什么新问题
5. 它具体是怎么做的（实现机制）

## 第 3 段：用五问拆「提示工程」（L325 等）

### 五问拆解

1. 前置问题：模型通用，只拧得动输入，输入怎么拧说不清
2. 解决了：把「任务定义」从训练期下放到输入期，不改参数、不微调
3. 解决不了：塞不下窗口、稳不住格式、保证不了推理、涨不了能力
4. 引入：prompt 变工程资产、提示注入、措辞脆弱、调 prompt 像炼丹
5. 怎么做（演进线）：零样本→few-shot→CoT→结构化输出约束→被模型内化

### 关键洞察

第 3、4 问是「演进」的引擎——提示工程解决不了的、引入的，恰好是后续每个「工程」的起点：塞不下→上下文工程；稳不住→先打补丁后被结构化输出吃掉；保证不了→CoT 后被推理模型吃掉；提示注入→上下文层护栏；prompt 资产管理→系统提示词工程、Agent Skills。

### 收口

提示工程里有吃不掉的部分：**意图澄清**（书 L253-255，GPT-5.6 先问清用户真实意图）。「用户自己没说清想要什么」不是模型能力短板，是需求本身的模糊，模型再强也猜不透。所以这一手是语义层，不会随模型变强而消失，反而会随模型越自主越吃香。提示工程的寿命取决于它手里还剩几个「模型补不上的短板」——现在主要剩「意图」这一层。

## 第 4 段：五概念 × 五问总表

| 概念 | ① 前置问题 | ② 解决了 | ③ 解决不了 | ④ 引入的新问题 | ⑤ 怎么做 |
|---|---|---|---|---|---|
| 提示工程 | 模型通用，只拧得动输入 | 任务定义下放输入 | 塞不下、稳不住、涨不了 | prompt 资产、提示注入 | few-shot→CoT→结构化，后被内化 |
| 上下文工程 | prompt 只是一句话 | 视野整体管理 | 信息充分 ≠ 行为正确 | 污染、压缩损失 | 静态前缀+轨迹、RAG、渐进式披露 |
| Harness 工程 | 能做事 ≠ 可靠做事 | 约束/验证/纠正 | 治理 ≠ 理解、自审不可靠 | 治理复杂度、误拒绝 | 默认关闭、风险评级、结构化验证、熔断 |
| Loop 工程 | 单次装不下长程自治 | 跨轮次持续运转 | 目标漂移 | 死循环、过度执行 | 停止条件、Init+Exec 分工、交接产物 |
| Graph 工程 | 单循环装不下混合系统 | 显式图+状态持久化 | 图正确性难验证 | 编排复杂度、过早抽象 | LangGraph/ADK graph workflow |

### 规律一：问题接力链

每一环的「③解决不了 + ④引入」正好是下一环的「①前置问题」：

```
提示工程 →(塞不下/注入)→ 上下文工程 →(信息全≠对/污染)→ Harness
   →(治理≠理解/复杂度)→ Loop →(目标漂移/死循环)→ Graph
```

真实演进逻辑不是「层层包含」，而是「问题接力」：每一层把上一层的尾巴接过来当自己的头。每一层不是「上一层不够好所以加强」，而是「上一层的盲区漏出了问题，被迫新开一个维度去堵」。

### 规律二：③「解决不了」就是补丁层/语义层的分界判据

判据一条：看 ③ 是不是「模型变强也消不掉」。消得掉是补丁层（提示工程的格式/推理），消不掉是语义层（Harness 的自审不可靠、Loop 的目标漂移、意图澄清）。

## 第 5 段：Graph 工程是演进的终态吗

### 碰撞记录

- 判断：不是终态，是「工程范式命名」这条线的**转折点**。三个理由：
  1. 按问题接力规律，Graph 还有 ③（图正确性难验证）+ ④（编排复杂度），链条还能续。
  2. Graph 的盲区换了性质——从「模型的问题」（塞不下、格式不稳、会幻觉）变成「工程自身的问题」（图对不对、怎么维护、太复杂）。续的方向不再是一个新的「XX 工程」，而是两条岔路：岔路 A「评估与进化」（书 7-9 章：边界集+保留集、回归、从轨迹生成更新）；岔路 B「向简单回归」（复杂度到顶，甚至「让模型自己画图」，又是工作流→自主张力的重演）。书的目录本身就是证据：作者在「构建」轴上命名到 Graph 就停了，之后是评估、进化、协作——换了一条轴。
  3. Graph 像终态只因为它是 2026 年 7 月最新的滞后指标（读者 H2），作者把它写成弧线末端是「当下视角的截断」，不是「逻辑终点的证明」。
- 收口：链条没有「范式终态」，只有「轴切换」。真正让轴停下来的不是某个范式，而是你是否接受「模型能力存在硬边界」这个前提。

## 第 6 段：Loop 工程深入（L331、L513、L105、L73、L416）

### 为什么需要跨轮次

不是设计者的选择，是任务客观属性：①窗口是硬上限（轨迹填满，想不跨都不行）；②时间跨度（几小时到几天，进程会重启、会话会结束）；③任务天然持续（常驻助手、定期任务，没有一次性终点）。

### 跨轮次需要解决什么

一句话：把「状态」从上下文里逼到了上下文外。单次运行状态（轨迹）全在上下文里，模型天然记得一切；跨轮次必须把状态搬出上下文，于是长出四个单次运行里不存在的问题：状态怎么存/传（交接产物、受控工作目录）、怎么续（避免重复/漏做）、怎么判完成（持续任务无自然终点 + 模型倾向过早完成）、下一轮谁触发（事件触发工具 / 外部调度）。

### 粒度澄清（读者追问「一次调用」后）

| 粒度 | 叫什么 | 是什么 |
|---|---|---|
| 1 | 一次调用（one call） | 发一次请求、拿一次响应（token 上限作用在此） |
| 2 | 一个回合（one iteration） | 一次完整「想→做→看」 |
| 3 | 一次会话/运行（one session/run） | 从请求到完成的完整轨迹 |
| 4 | 跨轮次（across sessions） | 多条会话接续 |

「跨轮次」跨的不是「一次调用」，是「一次运行」。调用之间是模型在同一份上下文里来回；运行之间，是上一份上下文已经装不下或中断了，得靠外部产物把下一份上下文重新搭起来。轨迹 = 动态消息历史 = 上下文里「静态前缀」之外那后半段（书 L167 正式术语）。

### 多大的任务需要跨轮次

判据：轨迹长度撞上窗口容量，或运行时长超过一次会话的物理上限。临界点 = 窗口容量 / 单步轨迹消耗。量级感：几分钟几十步不用跨；几十分钟几百步要压缩或跨；几小时到几天必然跨。收口：跨轮次和「扩大窗口」是同一个问题（让模型记得够多、接得起来）的两条路线，任务跟着窗口一起涨，所以 Loop 不会消失。

### 「大多数任务不需要 Loop」的两次纠偏

- 第一次（我理解偏了）：读者说「大多数任务不需要 loop」，我误以为他要说「该不该做 Loop」。纠偏要点：任务需不需要 Loop 提交前不可知（Agent 自主跑，轨迹会意外变长）；工程必要性按失败代价加权，不是按任务数量加权（少数长任务失败一次顶几百个短任务）。
- 第二次（读者澄清真实意思）：读者说「长周期运行的任务其实并不多」。承认事实：长周期任务在绝对数量上确实是少数。但指出它指向的更深问题——Loop 的普适性断崖：前三个工程（提示/上下文/Harness）几乎人人撞上，Loop/Graph 只有少数长周期/复杂编排场景才撞上，却在叙事里保持「层层递进、同等重要」的假象。结论：Loop 的地位是叙事撑起来的，不是任务量撑起来的。

### Loop 怎么做（书第 1 章散落的四块，书明说第十章展开）

1. 任务怎么拆/怎么接：初始化 Agent（设置环境、分解任务列表）+ 执行 Agent（每个会话增量推进）+ 交接产物（handoff artifact）——记忆不留在上下文里，落在产物上（L513）
2. 状态怎么落地：受控虚拟工作目录（保存计划、中间结果、日志、产物，限定路径/容量/文件类型）（L105）
3. 下一轮谁拉起：事件触发工具（邮件/定时/Webhook）（L73）
4. 什么时候停：停止条件（最终输出工具、无工具调用响应、最大轮数、不可恢复错误）（L416/L418）

统一图景：外层循环（Harness 管：状态落地/事件触发/停止判据）包内层循环（ReAct，模型自管「想→做→看」）。里层模型自己会走；外层必须 Harness 管——一跨会话，模型自己就管不了（看不到全貌、倾向过早收工）。

### Loop 相比 Harness 有没有新概念

- 零件层面：零新概念。工作目录=上下文管理/工具接口（L105 本就在工具一节）、事件触发=工具五大类之一（L73 明说归入工具体系）、停止条件=约束、交接产物=外部产物更新（L133）。
- 问题层面：提出了一个 Harness 没提过的新问题——把两个在单次运行里**被默认掉**的东西第一次逼成显式对象：调度权（谁来发现下一件该做的事，单次里 ReAct 自推进根本不用问）和完成判据（何时才算真正完成，单次里「返回最终答案」即结束）。
- 收口：**Loop 提出了一个新问题，但没为它发明任何新答案。Harness 是「新概念 + 新零件」，Loop 是「新问题 + 旧零件」。** 这是它与 Harness 的根本差距——不配平级，但也非纯换词。

## 第 7 段：编排模式：工作流与自主（L370-454）

### 结构标注

决策阶梯：单次调用 → 工作流 → 自主 Agent。工作流=确定性路径（订机票四节点/文生图两节点），优势=流程控制+安全（攻击面限制在节点内），局限=缺变通；自主 Agent=动态路径（本质=ReAct），适用开放式问题，代价=延迟+复合错误；混合（n8n）；框架对比表。

### 主碰撞：作者的判据就是「可枚举性」

作者 L374 的选择标准：「能清晰分解为固定子任务 → 工作流；需要动态决策 → 自主 Agent」。翻译过来 = 可枚举则工作流、不可枚举则自主——与读者核心判据「可枚举则进工具/代码，不可枚举才进模型」是同一个形状，作者没点破。

裂缝：作者把「可枚举」理解成「子任务固定」（静态分解），更准的是「路径可枚举」（状态/转移/停止条件能否穷举）。真实任务几乎都是「路径大部分可枚举 + 小部分不可枚举」，所以纯工作流和纯自主都是极端，真实答案永远是混合——作者自己 L428 用 n8n 承认，标题却维持二分。与「层层包含」同一个毛病：偏爱干净二分，真实系统是连续混合。

### 补刀：工作流的「路径安全 ≠ 节点内安全」

作者说工作流安全，因为「攻击面限制在单个节点内」（L389）。工作流只枚举了路径，没枚举节点内行为：路径代码写死、模型跳不到别的分支——没错；但节点内 LLM 被注入，路径没错、钱可能错（付款节点里 LLM 生成的金额被篡改）。节点内输出仍需 Harness 的「验证」（结构化校验）兜底。

### 判据升级（读者未回应，转为指定下一节）

「工作流 vs 自主」不该是两种模式，而是「路径可枚举度」这条连续谱上的两端；「可枚举」的判据该从「进不进工具」推广到「哪段路径交给代码、哪段交给模型」。

## 第 8 段：护栏与安全性（L456-494）

### 结构标注

三层护栏按「被绕过的难度」排（不是处理顺序）：上下文层（管能看到什么：相关性/安全分类器/内容审核/规则保护；Anthropic Constitutional Classifiers 的规则驱动+上下文联合判断+两级筛查）→ 执行层（管能做什么：工具风险评级、独立审查进程、最小权限、沙盒、人在回路、PII 过滤）→ 数据层（管世界最终能被改成什么样：行级安全、约束校验器、受控视图、受信任运行时）。人工干预：超过失败阈值、高风险操作。

### 主碰撞：排序轴 =「决策离模型多远」

三层真正的排序轴是「离模型有多远」：上下文层靠模型自己在上下文里判断（L474 自认死穴：「处在同一个上下文里的 Agent，很难判断自己是否已经被注入」——这就是「自审不可靠」原文）→ 执行层判断挪到上下文之外（L476「否则它会和被注入的 Agent 一起沦陷」）→ 数据层完全不经过模型（L478「即使提示注入得手、代码漏写权限判断，越权操作仍会在数据层被拒绝」）。三层护栏 =「自审不可靠」原则在安全域的完整展开，从「让模型自己判断」一路退到「模型根本够不着」。与读者「状态栏该读框架执行日志而非对话文本」同一条线。

### 判据升级：可枚举 ≠ 模型无法绕过

读者原判据「可枚举则进工具」，理由是「可审计、模型无法绕过」。三层护栏暴露二者不是一回事：上下文层的黑名单/正则**可枚举但可绕过**（注入时变形绕开）；数据层的行级安全/数据库约束**可枚举且绕不过**。更准的判据：「可枚举 + 模型够不着，才进工具（的强制层）」。「进工具」从一维（进不进）拉成两维（进哪一层）。

### 裂缝

L458「先针对已识别的风险设置护栏，再发现新漏洞时逐步添加」 vs L545「安全是架构问题，不是上线前打补丁」——「逐步添加」描述的正是「打补丁」。真相：上下文层和执行层本质是反应式的，永远追着已知攻击跑、慢一步；真正配得上「架构级」的只有数据层。

### 读者回应与纠偏（「多数场景下还是比较安全的」）

- 读者判断：多数场景下还是比较安全的。
- 纠偏：「多数场景安全」说的是**攻击概率低**，不是**防御完备性高**。攻击者不按概率分布来，专挑最薄弱的 1% 打。这是期望值思维 vs 最坏情况思维的差别——攻击者就是专门制造最坏情况的人。
- 但捞出一个对的部分：不是所有规则都要「模型够不着」。数据层是重型机制，普通规则上执行层就够。操作判据是**按代价分层**：代价小（读文件、查信息）→ 可枚举、进工具就够；代价大（不可逆/资金/权限）→ 才必须「模型够不着」的数据层兜底。
- 收口：安全决策不问「多数场景安全吗」，只问「少数不安全的场景，代价有多大，你有没有为它单独准备一层兜底」。

## 题 1 ★★：如果能给 Agent 增加一项能力（更强的模型 / 更丰富的上下文 / 更多的工具），你会选哪个？什么条件下选择会改变？

## 题 2 ★★★：ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

**读者回答（提问式）：**

> 第二题是不是压缩？

**点评（伴读）：**

- 压缩是辅路，主路是「前缀复用」（KV Cache）——这道题考的不是压缩，是 append-only。
- 二次方从哪来：轨迹只增不改、每轮线性变长，每轮重读全部，累计 L + 2L + ... + nL ≈ O(n²)。
- 主路：前缀复用——轨迹只追加、不改前面，前缀的 KV 计算可缓存，每轮只算新增段，O(n²)→O(n)。题目里「缓存读取量」这个词就是冲着它来的。
- 辅路：压缩/截断/外置——从源头缩短轨迹长度，降的是「每次读多长」，不是「减少重复读」。
- 书 L523 证据：「第二章的 KV Cache 前缀稳定性是它的性能形态——改动越靠前，作废的缓存越多」。
- 收口：这道题问的不是「怎么把内容变短」（压缩），是「怎么让缓存不失效」（append-only 纪律）。

## 题 3 ★★：模型即 Agent 趋势下，两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

**读者回答：**

> 模型再强，看到什么东西也不是模型可以决策的。长期来看，有一些东西可以被模型内化。但是 Agent 框架在可靠性、稳定性上仍然不可替代。

**点评（伴读）：**

- 亮点：「看到什么归框架」与「可靠性不可替代」两点抓得准。
- 精确化：不是「看到什么不是模型能决策的」，而是「看到什么的『空间』不是模型能定义的」——模型能决策空间内的选择（RAG 搜什么、自主调哪个感知工具），但观察通道的定义与边界归 Harness。定义可枚举→框架，选择不可枚举→模型（咬合读者「可枚举」判据）。

## 题 6 ★★：设计航班订票客服系统，选工作流还是自主 Agent？能否混合？

**读者作答（以退款场景置换题目例子）：**

> 在生产中是需要综合使用的。比如关于退款的部分，必须使用工作流，但是关于退款申请的部分，可以使用自主 Agent。

**点评（伴读）：**

## 题 7 ★★★：工具大部分低风险、特定参数组合下高风险（如 delete_file 删普通 vs 系统文件），如何设计动态风险评估？

**读者作答：**

> 本质上是除了判断工具本身的安全性，还得看工具作用的对象。

**点评（伴读）：**

- 本质抓对：风险不是工具的固有属性，是「工具 × 作用对象」的组合属性（delete_file 删临时文件低风险、删系统文件高风险）。
- 补第三个变量：风险 = f(工具, 对象, 发起上下文)。攻击者专挑「对象看着普通」的调用下手（诱导 Agent 读敏感数据再删普通文件），所以发起上下文是风险变量；且其评估不能靠模型自查（自审不可靠），靠外部信号（调用来源、审批链、行为异常检测），呼应 L476「复核必须上下文之外」。
- 机制设计：①调用前评估器（pre-call，执行前对 {工具, 参数, 对象} 算风险，非执行后查）；②对象敏感规则 + 保护名单（系统文件/生产库/资金对象默认拒绝、显式白名单授权——故障安全默认 L285）；③分级响应：低→执行 / 中→dry-run/预览/确认 / 高→人工审批（L476/L107）。
- 收口：动态风险评估 = 把风险从工具级静态属性拆成「工具 × 对象 × 发起上下文」的组合计算——对象与发起上下文两维都是「模型看不到全局、外部机制才看得到」的地方。

## 题 8 ★★：受限的动作空间（只能从预定义选项中选择）在什么场景下反而优于开放式？

**读者作答：**

> 我感觉很多吧，资金安全敏感的都可以是这样。

**点评（伴读）：**

- 对，「很多」，但统一判据是两条同时成立：①正确的动作集合可枚举（合法做法就那几种）；②开放的组合空间危险（不可逆/高代价/强约束）。资金安全敏感恰好两者都占。
- 为什么受限更好：①防呆（书 L349 ACI：让错误无法发生而非提醒别犯错——SIM 卡缺角、微波炉门）；②约束的强制实现（受限 = 约束在动作层的落地，状态机流转靠「选项里根本没有非法迁移」）；③可审计（决策集合写死，审计面小）。
- 开放何时更好：正确动作不可枚举或探索本身有价值（Coding Agent 写任意代码、搜索 Agent 生成任意查询）——枚举不完，开放是唯一选择。
- 收口：开放 vs 受限不是「高级 vs 保守」，是「可枚举判据」的极端形态——正确动作集合可枚举 → 连动作都枚举完（受限）；不可枚举 → 才放开（开放）。

## 题 9 ★★：人工干预要求优雅移交控制，但用户不在线/响应慢/指令模糊时，Agent 怎么办？

**读者作答：**

> 这个还是分级，本质上看移交的是什么任务，无法容忍的错误，必须用户确认。

**点评（伴读）：**

- 分级是正解，判据（错误容忍度）抓对；但更可操作的轴是「可逆 vs 不可逆」：
  - 不可逆 + 高代价（资金/删除/发布）→ 挂起，等用户确认，绝不猜着执行；
  - 可逆 + 低代价（查询/草稿/整理）→ 先干，产出结果等审——「先做能回滚的，挂起不能回滚的」；
  - 模糊指令 → 产出「我的理解 + 可选方案」，可逆部分先执行，不可逆部分等确认。
- 离线机制：挂起队列（不阻塞其他任务）+ 批量确认（一次性给待确认清单，不逐条打扰）+ 可逆任务按授权代理执行、事后汇报。
- 收口：整章答案收敛为同一句话——「可枚举 × 可逆性」决定一切（进不进工具/工作流还是自主/受限还是开放/人工确认还是自动）。本题即该判据在人工干预场景的翻版：无法容忍的错误 = 不可逆 = 模型够不着 = 必须外部的人确认。

## 题 10 ★★★：实现好的设计原则的具体工程手段会随模型进步而过时，试举一例并说明理由。

**读者作答：**

> 最后一题：few shot，这个算嘛

**点评（伴读）：**

- 教科书级答案——书 L408 自己就把 few-shot 当成「被内化的工程手段」头号例子（「few-shot 示例被指令微调和推理模型内化了」）。
- 为什么过时：few-shot 补的是「任务理解/格式跟随」这类模型能力短板；SFT 训练数据里全是「示例-答案」对，模型参数已编码，再塞例子边际收益趋近于零。过时是渐进的（模型强了从「值钱」变「放不放都行」），对应 L121「模型每内化一层，Harness 卸下一层」的节奏。
- 与「意图澄清」对照（判据一条：补的是谁的短板）：
  - few-shot 补模型的能力短板 → 会被内化（过时）；
  - 意图澄清补需求本身的模糊 → 不会（模型再强也猜不透含糊需求）。
- 收口：读者已非背答案，而是用「补丁层 vs 语义层」判据筛答案——这题是全程判据的收官验证。
