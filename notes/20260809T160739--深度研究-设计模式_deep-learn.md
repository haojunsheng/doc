## 阶段一：逐层深入（W1-W5）

### W1: 面向对象思想层 —— "你在写的是 OO 还是披着 OO 皮的过程式代码"

- **假设**：OOP 的优势只在**大规模复杂程序**上成立；小规模程序面向过程反而更优。贫血模型 MVC 流行不是因为它对，而是因为它简单且业务系统大多不复杂。
- **MECE 拆解**（对应 02 章）：
  - 子假设 1.1：封装/抽象/继承/多态各自解决的是不同的工程问题（隐藏实现/隔离变化/复用/扩展点），不是一套话术 → 验证方式：给每个特性找一个"没有它会怎样"的反面代码例子
  - 子假设 1.2：接口 vs 抽象类的区别本质是"has-a 行为契约 vs is-a 复用层次" → 验证方式：用普通类分别模拟接口和抽象类（02-08 讲的练习），说出什么场景模拟不出来
  - 子假设 1.3："多用组合少用继承"的判据是层次深度和复用方式，不是绝对禁令 → 验证方式：举出一个继承明显优于组合的例子（如模板模式场景）
- **动手验证**：**接口鉴权功能写两遍**（02-13/14 讲）——第一遍故意用面向过程写（一堆 static 工具方法 + Map 传参），第二遍重构成 OO。对比两遍代码在"新增一种鉴权方式"时改动的行数。
- **周末产出**：一段 200 字讲解《贫血模型 MVC 为什么违背 OOP 却依然流行》，发给自己或笔记，能用大白话讲清 = 到位
- **DIKW 本周锚点**：数据→信息。能从"面向对象四大特性"这堆术语里讲出它们之间的逻辑关系
- **失败日志**：本周必须记录 ≥1 条。高发点：充血模型 DDD 钱包系统（02-12）看不懂——大概率是领域驱动的前置知识缺口，记下缺口而不是跳过

### W2: 设计原则层 —— "原则是模式的宪法"

- **假设**：SOLID 中真正高频显式使用的是 SRP、OCP、DIP 三条；LSP 和 ISP 在 Java 实践中多数时候被隐式满足，刻意检查的回报低。KISS 和 YAGNI 才是日常决策中调用频率最高的原则。
- **MECE 拆解**（对应 03 章，原则按"针对什么问题"分，不重不漏）：
  - 子假设 2.1：SRP/ISP/LOD 是一族——都在回答**"边界划在哪"** → 验证方式：对同一个类（如课程的用户类），分别用三条原则切一刀，看切出来是否不同
  - 子假设 2.2：OCP/LSP/DIP 是一族——都在回答**"扩展点怎么留"** → 验证方式：写一个不用 OCP 的 if-else 版功能，再按"对扩展开放"改造，数改动面
  - 子假设 2.3：KISS/YAGNI/DRY 是一族——都在回答**"什么时候忍住别写"** → 验证方式：从自己过去的项目里找一段"过度设计"的代码，说出它违反了哪条
- **动手验证**：**性能计数器框架**（03-25/26 讲）——这是非业务通用框架的完整需求分析→设计→实现练习。要求：先自己写设计文档（类图 + 为什么这么分），再看课程答案，记录分歧点。
- **周末产出**：一张"原则族谱图"——10 条原则按上面三族组织，每条配一个**自己造的**违反示例（不是抄课程的）
- **DIKW 本周锚点**：信息→知识。标志：看到一段代码能不假思索说出"这违反了 X 原则"，而不是"感觉不太好"
- **失败日志**：本周必须记录 ≥1 条。高发点：控制反转/依赖反转/依赖注入三个概念（03-19）绕晕——画一张三者关系图，画不出来就是失败日志素材

### W3: 规范与重构层 —— "重构的安全网是测试"

- **假设**：没有单元测试覆盖的重构 = 赌博；"可测试性"本身就是代码质量的探针——不好测试的代码几乎必然设计有问题。
- **MECE 拆解**（对应 04-05 章）：
  - 子假设 3.1：重构分大重构（架构级，靠设计原则指导）和小重构（函数级，靠规范指导），两者手法完全不同 → 验证方式：各举一个课程中的例子归类
  - 子假设 3.2：可测试性差的具体根因只有有限几种（静态方法、单例、new 硬编码依赖、外部资源直连） → 验证方式：在 ID 生成器代码里逐条找
  - 子假设 3.3：异常处理选型（NULL/错误码/异常/空对象）有可判定的决策规则而非口味 → 验证方式：总结出自己的决策树，再用 04-36 讲的答案校准
- **动手验证**：**ID 生成器重构全流程**（04-34/35/37 讲）——先写清单列出你能发现的所有质量问题，再动手重构，**全程要求先补单元测试再动代码**。最后对照课程清单，统计你的召回率（漏了几个问题）。
- **周末产出**：一份个人版《重构 checklist》——发现问题的信号清单（如"函数超过 30 行""参数超过 4 个""出现魔幻注释"），从本周练习中提炼，以后 code review 直接用
- **DIKW 本周锚点**：信息→知识。标志：你能预判"这段代码明天需求一变会死在哪"
- **失败日志**：本周必须记录 ≥1 条。高发点：给遗留代码补测试时发现根本测不了——这本身就是最好的一条失败日志，记下根因属于哪一类

### W4: 创建型 + 结构型模式 —— "对象怎么生、结构怎么搭"

- **假设**（H3 首次实战检验）：不看课程答案，面对"创建逻辑复杂"和"接口不兼容"两类问题，自己能推导出与标准模式同构的解法。
- **MECE 拆解**（对应 06-07 章，按 GoF 标准分类）：
  - 子假设 4.1（创建型）：工厂模式的唯一正当理由是**创建逻辑复杂**（06-44 的争议点），为简单 new 包一层工厂是过度设计 → 验证方式：审视你过去项目里的每个工厂类，逐条判定"正当/过度"
  - 子假设 4.2（创建型）：单例模式的本质问题是**全局状态的隐式耦合**，替代方案（DI 容器管理）严格更优 → 验证方式：把 06-42 讲的替代方案亲手实现一遍
  - 子假设 4.3（结构型）：代理/适配器/桥接/装饰四者的区别不在代码结构（结构几乎一样），在**意图** → 验证方式：不看 07-51 讲，自己写四者的意图一句话定义，再对照
- **动手验证**：两个 mini 框架二选一必做、时间够都做：① **mini DI 容器**（06-45 讲，支持构造函数注入 + 注解即可）；② **桥接模式消息推送**（06-49 讲，消息类型 × 推送渠道两个维度独立扩展）
- **周末产出**：一张"四兄弟辨析图"（代理/适配器/桥接/装饰：同一个 `Wrapper` 结构，四种意图），配 JDK/Guava 里各自的一个真实用例
- **DIKW 本周锚点**：知识层。标志：能说出"模式的标准实现"与"这个场景下我的裁剪版"差异在哪、为什么裁剪是合理的
- **失败日志**：本周必须记录 ≥1 条。高发点：H3 推导练习失败——你设计的和工厂模式不像。这不是失败是数据：记下偏离在哪，它揭示你缺的到底是原则理解还是模式经验

### W5: 行为型模式 —— "对象之间怎么协作"（量最大的一周，18 讲）

- **假设**：行为型模式里真正高频的只有 5 种——观察者、策略、模板、职责链、状态；迭代器/访问者/解释器/备忘录/命令/中介/享元在业务代码中出现率 <5%，但在框架源码中出现率很高（这是它们的真实栖息地）。
- **MECE 拆解**（按"协作关系"维度切，与 GoF 分类对齐）：
  - 子假设 5.1（通知族）：观察者 vs 中介的区别是**一对多广播 vs 多对多枢纽** → 验证方式：实现 mini EventBus（08-57），然后说出一个它退化成需要中介的场景
  - 子假设 5.2（算法族）：策略 vs 状态 vs 命令的区别是**算法可换 / 状态驱动行为 / 请求对象化** → 验证方式：用策略模式消除一个真实 if-else 链（08-60），再指出它换成状态模式的临界点
  - 子假设 5.3（流程族）：模板 vs 职责链 vs 访问者的区别是**骨架固定步骤可变 / 请求沿链传递 / 数据结构稳定操作易变** → 验证方式：实现敏感词过滤职责链（08-62），画出 Servlet Filter 的同构图
- **动手验证**：① **mini EventBus**（08-57，异步非阻塞，允许用 Guava EventBus 对照）；② **敏感词过滤框架**（08-62，要求过滤器可插拔、顺序可配）。每个都要求"先自己设计 30 分钟再看课"。
- **周末产出**：一张**行为模式决策树**——从"我想让 X 可替换/可通知/可扩展"出发，终点是具体模式。这张图是 C 级目标的核心资产，W6/W7 要拿它去源码里对照
- **DIKW 本周锚点**：知识层。标志：别人描述一个协作问题（"多个模块都要响应下单事件"），你 30 秒内给出模式候选和排除理由
- **失败日志**：本周必须记录 ≥1 条。高发点：访问者模式（08-68）双分派想不通——正常，它是 23 种里最反直觉的，把你卡住的思维拐点记下来

## 验收标准：学习结束时你能回答这 5 个问题

Q1（从零设计）：给你一个"支持多种规则的热更新限流框架"需求，你能独立完成需求分析→类设计→核心实现，并讲清每个类为什么存在吗？（W7 直接验证）
Q2（判断新信息）：看到一篇《XX 新框架用了 YY 设计》的文章，你的判断框架是什么？（参考答案形态：它解决的真实问题是什么→这个模式在此场景的成本是什么→有没有更简单的方案（KISS/YAGNI 检验））
Q3（定位失败根因）：接手一段"改不动"的遗留代码，你的定位顺序是什么？（参考答案形态：可测试性探针先行 → 依赖硬编码排查 → 原则违反点清单 → 大重构还是小重构的判定）
Q4（假设复盘）：H1/H2/H3 各对了多少？错的那部分，错因是"领域理解不够"还是"假设本身提得不可证伪"？
Q5（可证伪预判）：你对"设计模式知识在 AI 编程时代的价值"给出一个具体预判（示例：AI 生成代码后，人的核心价值从"写模式"转移到"评审设计决策"，原则层知识价值上升、模式记忆价值下降），以及什么证据出现会让你承认判错。
