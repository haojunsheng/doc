# 全局地图

## 一句话摘要

第四章把 Agent 的"手脚"拆成完整工程：先定能力表达形态（专用工具 vs Skill+通用执行器），再靠 MCP 统一互操作生态，然后逐类深入感知/执行/协作三类主动调用工具的安全与设计原则，最后解决"工具太多时怎么被找到"。

# 逐段伴读记录

## 停驻点 1：幂等性与取消语义

- 书给两条手段：唯一标识去重、先查询后变更；不可幂等操作用"预检-确认"两段式
- 读者本行有书里没有的第三层：冲正（反向交易）——需要业务语义，属语义层
- 对话被读者主动叫停（"先不往结算上扯了"），未继续展开

## 停驻点 2：4.7 主动工具发现

- 关键洞察 1（铁律松动）："工具定义必须在上下文最前面"不再是铁律——schema 追加末尾、固定在首次注入位置、模型后训练理解散落定义。与第一章"补丁层会被模型吃掉"同构：上下文布局约束被模型能力内化后松动
- 关键洞察 2（元认知回声）：主动发现 = Agent 要自己声明"缺工具"，比"被动从列表挑"更难——依赖"知道自己缺"。第二章思考题 7 的问题在工具侧重演。作者的工程缓解：状态栏维护工具名列表 + 后训练内化
- Skills 路线：把"工具选择"（LLM 弱项）改写成"读文档"（LLM 强项）——与第二章"上下文学习是检索而非推理"一脉相承
- 模型原生工具 vs Skill：JSON schema 可强制采样、模型好用但人改起来牵一发动全身；自然语言好写但 CLI 转义复杂、行为易漂移。按参数复杂度分流
- 作者论文第三次出现：可编辑可组合 KV Cache（skill = 可复用缓存对象, O(L) 拼接）

## 碰撞记录

- 读者对"skill 行为漂移是否明显"没有清晰体感 → 记录为"知道自己不知道"（元认知案例），挂到 W3 动手环节：连续用 skill 3 次，记录触发准确度+执行偏离度，区分随机噪声 vs 系统性偏差
- 读者两次拒绝被往结算领域拉 → 倾向：让 Agent 工程逻辑先在自己领域内自洽，用结算经验当"验证器"而非"脚手架"
