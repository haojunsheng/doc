## 阶段一：逐层深入（~5 周）

### W1: 分布式系统总纲 + 弹力设计（上）——故障是什么

- **假设**：分布式系统的所有难点都可以归结为"部分失败"（partial failure）——单机时代的假设（调用要么成功要么失败）在网络分区下全部失效
- **MECE 拆解**：
  - 子假设 1.1：分布式的难点清单是封闭且可枚举的（亚马逊实践那篇给的就是全集）→ 验证方式：读 21-22 篇，拿你在美团结算遇到的分布式问题逐条对号入座，找有没有对不上的
  - 子假设 1.2：弹力设计的模式集（重试/熔断/限流/降级/幂等/补偿）是"应对部分失败"的完备集 → 验证方式：读 41-45 篇，检查每个模式针对的故障类型是否互斥且穷尽
  - 子假设 1.3：监控是弹力设计的前提而不是补充 → 验证方式：读 24 篇（全栈监控），论证"没有监控时熔断阈值能否被正确设定"
- **动手验证**：写一个最小 demo——两个服务 A→B，B 注入 30% 随机失败 + 200ms 延迟抖动；A 分别实现"裸调用 / 只重试 / 重试+熔断"三种模式，用 wrk 或 hey 压测，对比成功率与延迟长尾。**预期你会亲眼看到"只重试"在 B 过载时雪崩**——这是陈皓"重试设计"篇核心论点的实证
- **周末产出**：一张"故障类型 × 弹力模式"矩阵图 + 200 字讲清"为什么只加重试可能让系统死得更快"
- **DIKW 本周锚点**：数据→信息（从"读过这些模式"到"能说清每个模式针对什么故障"）
- **失败日志**：本周必须记录 ≥1 条（demo 压测结果不符合预期是最理想的素材）

### W2: 弹力设计（下）+ 管理设计——把故障关进笼子

- **假设**：弹力设计的数据面（熔断限流降级）与管理设计的控制面（配置中心/网关/服务网格）是同一件事的两侧——控制面存在的唯一理由是数据面策略需要动态调整
- **MECE 拆解**：
  - 子假设 2.1：幂等、状态、补偿事务是同一问题的三个视角（"操作可以被安全地重复/恢复/撤销"）→ 验证方式：读 44-46 篇，用结算的"重复打款防护"场景检验三个视角是否等价
  - 子假设 2.2：服务网格（Sidecar/Istio）的本质是"把弹力设计从业务代码下沉到基础设施"，而非新技术 → 验证方式：读 54-55 篇，列出网格接管了 W1 矩阵中的哪些格子、哪些格子它管不了（提示：业务幂等它管不了）
  - 子假设 2.3：分布式锁和配置中心是"控制面的一致性基础设施" → 验证方式：读 52-53 篇，回答"为什么配置中心用 AP 而分布式锁要 CP"——这个 trade-off 就是本周的试金石
- **动手验证**：把 W1 的 demo 升级——用 Redis 实现一个带超时和 fencing token 的分布式锁保护 B 的临界区；再故意制造锁超时但客户端继续执行的场景，观察没有 fencing token 时的数据损坏。**这是"管理设计"篇最值钱的一个实验**
- **周末产出**：一段 200 字讲解"服务网格为什么管不了业务幂等"，发给别人能看懂的那种
- **DIKW 本周锚点**：信息→知识（能判断"一个新出的流量治理框架解决了哪个格子的问题"）
- **失败日志**：≥1 条（fencing token 实验大概率会翻车一次）

### W3: 性能设计 + 结算场景映射——你的主场验证周

- **假设**：陈皓的性能设计模式（缓存/异步/数据库扩展/秒杀/边缘计算）在结算系统这个"强一致 + 低并发（相对 C 端）+ 高正确性"场景下，适用性会系统性打折——性能设计与一致性设计存在根本张力
- **MECE 拆解**：
  - 子假设 3.1：缓存的本质是"用一致性换性能"，结算场景的可缓存边界由业务容忍度决定 → 验证方式：读 58 篇，梳理结算系统中哪些数据可缓存（费率配置？）、哪些绝对不可（账户余额？），画出边界
  - 子假设 3.2：异步化的本质是"用时间换解耦"，代价是状态可见性延迟 → 验证方式：读 59 篇，分析结算流水线（计费→清分→结算→打款）哪些环节异步化是赚的、哪些是被迫的
  - 子假设 3.3：秒杀的"削峰+排队+限流"三板斧与结算的"资金峰值防护"同构 → 验证方式：读 61 篇，论证大促打款峰值能否用秒杀思路处理、差在哪（差在：秒杀可以拒绝，打款不能丢）
- **动手验证**：这是你的主场——不写 demo，做一次**真实架构复盘**：取你熟悉的结算系统一个核心链路，用 W1-W3 的全部模式做一次"模式覆盖度体检"（每个环节用了哪些模式、缺了哪些、缺的是有意还是疏忽），输出一份内部可分享的文档
- **周末产出**：那份结算链路模式体检文档（这是 6 周计划里最有面试价值的一份产出，L8/P7 面试讲系统设计时直接用）
- **DIKW 本周锚点**：知识层夯实（能回答"So what"：这个模式在强一致场景为什么失效）
- **失败日志**：≥1 条（体检中发现的"当时设计错了"的点是最真实的失败日志）

### W4: 编程范式 + Go 编程模式——代码层面的本质

- **假设**：编程范式之争（OOP vs FP vs 泛型）的本质是"组合方式之争"——所有范式都在回答"代码如何组合成系统"，差异只在组合的基元是什么（对象/函数/类型）
- **MECE 拆解**：
  - 子假设 4.1：Go 的设计是"组合优先"哲学的极端化（委托优于继承、接口隐式满足、组合优于类型层级）→ 验证方式：读 37、107-110 篇，用 Java（你的主力语言）的继承体系对照 Go 的委托，各写一个同功能小模块
  - 子假设 4.2：错误处理风格是范式的试金石——返回码、异常、函数式 Either 背后是不同的"错误是否是一等公民"世界观 → 验证方式：读 11-12、108 篇，论证为什么 Go 选择显式返回错误而不是异常（提示：和"错误的可见性"有关）
  - 子假设 4.3：修饰器/Pipeline/Map-Reduce 是函数式思想在工程界的三个化身 → 验证方式：读 34、113-114、111 篇，用 Aviator 规则引擎的执行链路对照 Pipeline 模式
- **动手验证**：用 Go 重写一个你熟悉的 Java 小工具（比如一个带重试和规则过滤的结算数据清洗器），强制使用 Functional Options + Pipeline + 显式错误处理，体会"组合优先"与"继承优先"的手感差异
- **周末产出**：一张"范式 × 组合基元 × 错误世界观"对照图 + 200 字回答"为什么陈皓说编程的本质是控制复杂度"
- **DIKW 本周锚点**：知识→智慧过渡（开始看到不同领域的相同结构：范式的组合问题 = 分布式的组合问题）
- **失败日志**：≥1 条

### W5: 区块链 + 练级攻略对照 + 趋势预判——"能判断"的验收周

- **假设**：用前四周建立的框架，可以独立拆解一个"陌生"领域（区块链对你是相对陌生的）并做出可证伪的趋势预判——这是 C 级深度的直接证据
- **MECE 拆解**：
  - 子假设 5.1：区块链的本质是"用算力成本换信任"，是分布式共识在"拜占庭环境"（参与者不可信）下的特例 → 验证方式：读 63-66 篇，用 W1-W2 的分布式框架对照：PBFT/PoW 和你熟悉的 Raft/Paxos 差在哪（差在参与者是否可信这一个变量）
  - 子假设 5.2：智能合约 = "规则引擎 + 不可变状态机"，和结算的规则引擎同构 → 验证方式：读 67 篇，论证 Aviator 规则引擎加一个"不可篡改审计日志"是否就是智能合约（差在去中心化执行环境）
  - 子假设 5.3：陈皓练级攻略中底层原理部分（系统知识/理论学科/分布式）在 2026 年仍 100% 成立，但工具链部分已被云原生 + AI 编程改写 → 验证方式：抽 75、77、82 三篇，逐条标注"仍成立/已过时/部分过时"，统计比例——这直接检验 H3
- **动手验证**：做"预判练习"——对 3 个 2026 年的技术趋势（如：AI Agent 基础设施、WebAssembly 服务端化、结算领域的实时化）各写一段 150 字预判，每个预判必须附带"什么证据会证明我错了"
