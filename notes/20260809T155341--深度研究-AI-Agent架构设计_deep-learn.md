## 阶段一：逐层深入（~7 周）

### W1: 上下文工程（第二章）——Agent 的"眼睛"，全书最关键一章

- **假设**：上下文是 Agent 能力上限的第一决定因素；上下文管理的四个手段（提示工程、Skills 按需加载、状态栏、压缩）各自解决的是不同层面的膨胀问题
- **MECE 拆解**：
  - 子假设 1.1："上下文 = 消息列表"，一切上下文技术都是在操作这个消息列表 → 验证方式：读 API 消息结构小节，用 `chapter2/` 代码打印一次真实请求的消息数组
  - 子假设 1.2：KV Cache 的三条核心结论决定了为什么"上下文前缀不能乱动" → 验证方式：记住三条结论（原理可略读），在实验中改动消息前缀观察缓存失效/成本变化
  - 子假设 1.3：提示注入是上下文工程的安全对偶——凡是能进上下文的都是攻击面 → 验证方式：跑提示注入攻防实验，亲手注入成功一次
  - 子假设 1.4：Skills 按需加载 + 状态栏 + 压缩，分别解决"提示词膨胀、工具列表膨胀、环境不感知、长度超限"四个不同问题 → 验证方式：为每个机制各跑一个 `chapter2/` 对应实验
- **动手验证**：`chapter2/` 至少跑通 3 个实验（必选：提示注入攻防、上下文压缩；自选 1 个）
- **周末产出**：一段 200 字讲解："如果让我给一个 Agent 团队的上下文设计做 code review，我会按什么清单查"（清单来自本章四个机制）
- **DIKW 本周锚点**：数据→信息（能说清"上下文工程包含哪些机制、各治什么病"）
- **失败日志**：本周必须记录 ≥1 条（哪怕只是"KV Cache 原理第一遍没读懂，先记结论"）

### W2: 记忆与知识库（第三章）——上下文的跨会话延伸

- **假设**：记忆和 RAG 本质是"上下文的时间维度扩展"——把不在当前消息列表里的信息，按需拉回消息列表
- **MECE 拆解**：
  - 子假设 2.1：用户记忆四种渐进策略的演进动力是"成本 vs 个性化深度"的权衡 → 验证方式：列出四种策略，各说出一个它优于前一种的具体场景
  - 子假设 2.2：RAG 的效果瓶颈通常在检索排序而非生成 → 验证方式：跑 `chapter3/` RAG 实验，分别只换检索方法/排序方法，对比回答质量
  - 子假设 2.3：Agentic RAG（让 Agent 自主决定何时检索、检索什么）优于固定流水线 RAG，但代价是延迟与不可控 → 验证方式：读对应小节，写出一个固定流水线会失败而 Agentic 会成功的查询例子
- **动手验证**：`chapter3/` 跑通 1 个 RAG 实验 + 1 个记忆策略实验
- **周末产出**：一张对比表：四种记忆策略 ×（实现成本 / 个性化深度 / 失败模式）
- **DIKW 本周锚点**：信息层巩固（能把记忆/RAG 挂进 W1 的知识结构图"上下文"分支下）
- **失败日志**：≥1 条

### W3: 工具（第四章）——Agent 的"手脚"

- **假设**：工具设计的好坏 = 动作空间设计的好坏；五类工具（感知/执行/协作/事件触发/用户沟通）的划分覆盖了 Agent 与世界交互的全部方式
- **MECE 拆解**：
  - 子假设 3.1：MCP 的价值是互操作标准而非新能力 → 验证方式：说清 MCP 出现前后，给 Agent 加一个新工具的工程成本差在哪
  - 子假设 3.2：执行工具的核心矛盾是"能力 vs 安全"，安全机制（沙箱、确认、越权防护）是 harness 的原型 → 验证方式：跑 `chapter4/` 危险操作防护实验，故意让 Agent 做一次越权操作看拦截
  - 子假设 3.3：事件驱动架构是把 Agent 从"请求-响应"推向"异步长任务"的关键 → 验证方式：画出同步 Agent 与事件驱动 Agent 在"打一通 2 小时电话"场景下的时序差异图
- **动手验证**：`chapter4/` 至少 2 个实验（必选：执行工具安全机制）
- **周末产出**：一段话回答："为什么 Pine 敢让 Agent 替用户谈钱？"——用本章的安全机制清单作答
- **DIKW 本周锚点**：信息→知识（开始能判断"这个工具设计安不安全"）
- **失败日志**：≥1 条

### W4: Coding Agent 与代码生成（第五章）——通用 Agent 的技术基座

- **假设**："Coding Agent + 文件系统"之所以是通用 Agent 的核心基座，是因为代码生成把"做新工具"变成了 Agent 的内生能力（自举）
- **MECE 拆解**：
  - 子假设 4.1：Coding Agent 的工作流是 ReAct 循环 + 文件系统这个特殊工具的组合 → 验证方式：读 OpenClaw 架构剖析，画出它的循环结构，标出与第一章通用 ReAct 的差异点
  - 子假设 4.2：代码生成的价值远超编程——辅助思考、构建知识库、动态造工具 → 验证方式：从 `chapter5/` 选一个非编程用途实验跑通（如用代码生成整理一个知识库）
  - 子假设 4.3：Agent 自举（Agent 写 Agent）是 Sutton 所说"设计实体"的工程实现 → 验证方式：跑自举相关实验，或写 200 字说清它和"模板生成代码"的本质区别
- **动手验证**：`chapter5/` 至少 2 个实验（其中一个必须是非编程用途）
- **周末产出**：一个 demo——让你正在用的 Coding Agent 为你造一个小工具，并记录它造的过程中你观察到的架构行为（调了什么工具、上下文怎么管）
- **DIKW 本周锚点**：知识层（能解释"为什么是代码而不是别的成为通用接口"）
- **失败日志**：≥1 条

### W5: 评估（第六章）——"没有评估就没有进步"

- **假设**：评估是 Agent 工程从"手艺"变"科学"的分水岭；评估体系 = 环境 × 数据集 × 评判方法 三个独立维度
- **MECE 拆解**：
  - 子假设 5.1：工具调用型与人机交互型是两种根本不同的评估范式，混用会得出错误结论 → 验证方式：各找一个适用场景，说清为什么另一种范式在该场景失效
  - 子假设 5.2：LLM-as-a-Judge 的可靠性取决于 rubric 设计而非裁判模型本身 → 验证方式：跑 `chapter6/` 评估实验，改 rubric 观察评判结果变化
  - 子假设 5.3：评估驱动选型的意思是"先建评估集，再选模型"，顺序不能反 → 验证方式：写出一个"先选模型后补评估"会踩的具体坑
- **动手验证**：`chapter6/` 至少 1 个完整评估实验（建小评估集 → 跑 → 出分 → 分析一个失败 case）
- **周末产出**：一份 mini 评估报告：对某个小 Agent 行为跑评估，找出 1 个失败 case 并定位到"上下文/工具/模型"哪一层
- **DIKW 本周锚点**：知识层深化（能区分"真的变好了"和"运气"）
- **失败日志**：≥1 条

### W6: 模型后训练（第七章）——B 档目标下抓论点，不抠推导

- **假设**：对 Agent 构建者而言，后训练的关键结论只有两条——"SFT 记忆、RL 泛化"和"数据与环境比算法更重要"；其余是训练工程师的细节
- **MECE 拆解**：
  - 子假设 6.1：预训练/SFT/RL 三阶段各司其职，SFT 教格式、RL 教能力 → 验证方式：用一个例子说清"这个行为该用 SFT 还是 RL 训出来"
  - 子假设 6.2：奖励设计的演进（二元→过程→"奖励结果、约束过程"）是在解决 reward hacking → 验证方式：说清验证路径惩罚为什么比纯过程奖励更抗 hacking
  - 子假设 6.3：Agentic RL 正在把工具调用能力直接训进模型参数，这会长期压缩上下文工程的生存空间（与本章立场对撞的反向假设） → 验证方式：读完后写下你站哪边——"上下文工程会被模型能力吃掉多少？"，给出你的比例估计和理由
- **动手验证**：本章数学要求最高，B 档允许降低动手强度：跑 1 个 `chapter7/` 入门实验（★级）或精读"SFT 记忆、RL 泛化"论证部分并复述给 AI 听
- **周末产出**：300 字立场文："模型变强后，上下文工程还重要吗？"（这是 W1 假设 H1 的第一次正面复审）
- **DIKW 本周锚点**：知识→智慧萌芽（开始看到"能力在参数里 vs 能力在上下文里"这个跨领域结构）
- **失败日志**：≥1 条

### W7: 持续进化（第八章）——运行经验 → 下一版能力

- **假设**：Agent 持续进化 = 学习信号 × 更新载体 的二维选择问题；四种载体（知识文档/Prompt 与 Skills/程序与 Harness/模型参数）按更新成本和风险排序
- **MECE 拆解**：
  - 子假设 7.1：三类学习信号（环境结果/过程规则/LLM Rubric）对应第六章评估体系的运行时版本 → 验证方式：画出 W5 评估体系与 W7 学习信号的映射图
  - 子假设 7.2：四种更新载体构成"成本×风险"光谱，多数团队应该优先更新知识文档和 Prompt 而不是参数 → 验证方式：为一个假想业务（如客服 Agent）排定四种载体的采用顺序并给出理由
  - 子假设 7.3：灰度发布与回滚机制是把"进化"从冒险变成工程的关键 → 验证方式：读候选版本验证小节，写出一个没有回滚机制会导致的真实事故场景
- **动手验证**：跑 1 个 `chapter8/` 实验，或设计一个"给自己常用的 AI 工具加一层经验沉淀机制"的方案（写到可执行粒度）
- **周末产出**：一张"学习信号 × 更新载体"矩阵图，每格填一个真实例子
- **DIKW 本周锚点**：智慧层入口（"评估—学习信号—更新载体—灰度"这条链就是任何自我改进系统的通用结构）
- **失败日志**：≥1 条

### W8: 多模态与多 Agent（第九、十章）——边界与终局，兼检验 H3

- **假设**：多模态/实时性的挑战本质是"上下文和工具的时间维度变连续了"；多 Agent 协作的价值集中在模态隔离或责任隔离的天然分工场景（检验 H3）
- **MECE 拆解**：
  - 子假设 8.1：语音 Agent 从串行流水线到端到端的演进，动力是延迟与情感信息损失 → 验证方式：画出两种架构的处理链路，标出延迟和损失各发生在哪一环
  - 子假设 8.2：Computer Use 和 VLA 是同一模式（截图/视觉 → 动作空间）在不同载体上的实例 → 验证方式：说出两者动作空间设计的异同
  - 子假设 8.3：多 Agent 分类框架（上下文共享/独立 × 对等/管理者/去中心化）中，"上下文独立 + 管理者"是当前最实用的形态 → 验证方式：用电话+电脑 Agent 案例解释为什么它恰好落在这一格；再找出一个"对等协作"更优的反例
- **动手验证**：跑 1 个 `chapter9/` 或 `chapter10/` 实验（语音 Agent 或多 Agent 翻译皆可）；若时间紧，改为精读电话+电脑 Agent 案例并画出协作架构图
- **周末产出**：对 H3 的裁决书——"多 Agent 什么时候值得？我最初的假设对了吗？"（300 字）
- **DIKW 本周锚点**：智慧层（能看到"模态隔离/责任隔离 → 架构分治"这个模式在软件工程、组织架构里同样存在）
- **失败日志**：≥1 条
