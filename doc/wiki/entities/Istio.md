# Istio

开源服务网格实现，为部署在 Kubernetes 上的微服务提供流量管理、安全和可观测性。

## 架构：Sidecar 代理

Istio 传统上使用 **sidecar 模式** —— Envoy 代理在应用 pod 内的 sidecar 容器中运行，透明拦截所有进出流量。

### Sidecar 代价

- **资源翻倍**：每个 pod 容器数翻倍（应用 + 代理）
- **运维面变宽**：代理配置增加另一个管理组件
- **调试链路变长**：流量经过代理后才到达应用
- **延迟增加**：每次请求额外网络跳数

## 核心能力

| 能力 | 描述 |
|------|------|
| **流量管理** | 负载均衡、熔断、重试、超时 |
| **mTLS** | 服务间双向 TLS 认证 |
| **可观测性** | 请求追踪、指标、访问日志（自动注入） |
| **安全** | 授权策略、限流 |
| **金丝雀发布** | 基于权重的版本流量拆分 |

## Istio vs ESB —— 核心对仗

这一对比是检验 [[H2]] 的关键：

| 维度 | Istio（服务网格） | ESB（企业服务总线） |
|------|------------------|-------------------|
| 统一层级 | 通信治理 | 业务编排 |
| 逻辑位置 | 分布式在代理中 | 集中式在总线中 |
| 失败原因 | 复杂性自我吞噬 | 业务逻辑神圣不可让渡 |
| 采用结果 | 渐进接受 | 被组织拒绝 |

关键洞察：网格成功是因为通信治理是没人想自己建的。ESB 失败是因为业务编排是核心能力，没人愿意外包。

## 演进：Ambient Mesh 与 eBPF

Sidecar 模式正受到挑战：

- **Ambient Mesh**：移除 per-pod sidecar，使用 namespace 级 waypoint 代理
- **eBPF**：完全绕过代理，在内核层注入可观测性和策略

这代表「下沉后的再优化」——把代理推向更深的 infra 栈（节点级 → 内核级），符合 [[H2]] 的单向下沉预测。
