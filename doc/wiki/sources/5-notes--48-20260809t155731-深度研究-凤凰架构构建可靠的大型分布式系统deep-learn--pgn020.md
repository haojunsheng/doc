# 深度研究——凤凰架构：构建可靠的大型分布式系统

**领域类型**: T 型（技术/工程）为主，M 型（心智/思维）为辅
**目标深度**: C（能判断）
**时间跨度**: ~5 周

## 主轴

> 用不可靠部件构造可靠的大规模分布式系统是否可行？

**中心论点**：凤凰式可靠——不追求部件不坏，追求整体对个体失败免疫。通过演进式视角、复杂度下沉基础设施、按组织做治理三大支柱构建可靠性。

## 核心假设

### H1 — 可靠性工程本质

可靠性不是消除失败，而是把不可靠节点的失败压缩到「可检测、可恢复」的窗口内。所有方案（共识、事务、容错、冗余）都在「恢复窗口大小 × 实现成本」平面上做交易。

→ **可证伪条件**：发现某个主流方案真的消除了某类失败（而非更快检测/更快恢复它）。

### H2 — 复杂度单向下沉

架构演进是单向的「复杂度下沉」：应用代码 → 框架类库 → 基础设施。每下沉一步，开发者就放弃一层定制权。判断范式成败看「下沉的东西大家本来就不想管的」。

→ **可证伪条件**：出现一个把复杂度从基础设施拿回应用层且大规模成功的案例。

### H3 — 结算系统终局形态

局部强一致（单库事务内）+ 全局最终一致（SAGA/对账）+ 事前幂等。纯 XA/2PC 退出在线链路，TCC 只在高价值、低并发、接口可控的链路划算。

→ **可证伪条件**：实际工作中看到 2PC/TCC 在结算核心链路成为主流方案且长期稳定运行。

## 动手验证

- **W1**: 同一结算场景（清分→结算→打款），分别用可靠事件队列、TCC、SAGA 写出状态机设计，推演每个中间态挂掉的恢复路径，产出三列决策矩阵
- **W2**: 跑 raft 官方可视化动画推演 leader 选举；本地起 etcd 3 节点集群，kill leader 观察重选举
- **W3**: 注入延迟故障，严格执行「metrics 定方向 → trace 定服务 → log 定代码行」的排查顺序并计时
- **W4**: minikube/kind 起集群，装 Istio，完成金丝雀发布 + fault injection
- **W5**: 45 分钟系统设计面试模拟 + H1/H2/H3 逐条修正

## 验收标准

学完后应能回答：

1. 从零设计日终结算系统：事务、幂等、对账各怎么选？
2. 面对宣称「取代 Istio、延迟降 80%」的新项目，先查哪 3 个信息？
3. 结算单卡在中间态、日志无异常，按什么顺序检查哪 5 个地方？
4. H1/H2/H3 五条证据是否成立/修正/推翻？
5. 给出一个可证伪的 2026-2028 预判。
