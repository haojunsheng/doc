# 深度研究——左耳听风（陈皓）：假设驱动学习计划 v2

> **领域类型**：H 型（T 为主 + M 为辅）——分布式架构与工程设计有可跑通的验证手段，技术领导力与成长篇看判断力
> **目标深度**：C（能判断）——面对新技术/新架构能独立做价值判断和趋势预判
> **时间跨度**：约 6 周（每周 12+ 小时，高强度冲刺）
> **学习方法**：假设驱动 + MECE 拆解 + 动手验证 + DIKW 自检

## 核心框架 H1-H3

**H1：分布式系统设计的本质是"对故障的妥协方案集"**
所有弹力/管理/性能设计模式都是同一件事的不同切面——在不确定环境中用确定性原语（幂等、重试、熔断、补偿）把故障关进笼子。

→ 证伪条件：W2-W3 发现某个模式无法归入此框架，或存在"与故障无关"的核心设计动机。

**H2：结算系统的稳定性瓶颈不在技术模式缺失，而在"业务语义与工程模式的映射"**
幂等、补偿、状态机在结算场景的难点是业务语义建模，不是技术实现。

→ 证伪条件：W3 把专栏模式映射到结算场景时，发现映射是机械的、难点全在工程细节。

**H3：陈皓 2018 年的判断框架在今天依然成立，但"程序员练级攻略"技能清单已部分过时**
底层原理（分布式、范式、系统知识）历久弥新，具体技术栈已被云原生和 AI 编程工具改写。

→ 证伪条件：W5 对照当前技术趋势预判时发现练级攻略的具体推荐仍然完全适用，或底层原理也已失效。

## 学习路径：阶段零到阶段五

### 阶段零：最小领域认知（~3 天）

读材料建立俯瞰视角：
- `开篇词-洞悉技术的本质，享受科技的乐趣.md` + `加餐-谈谈我的"三观".md`
- `96-高效学习：端正学习态度.md` + `97-高效学习：源头、原理和知识地图.md` + `98-高效学习：深度，归纳和坚持实践.md`
- `69-程序员练级攻略：开篇词.md` + `91-程序员练级攻略的正确打开方式.md`

产出：一张知识结构图（白纸/白板手画：以"洞悉技术本质"为中心，分出技术/成长/管理三支）。

### W1：分布式系统总纲 + 弹力设计（上）——故障是什么

- 子假设 1.1：分布式的难点清单是封闭且可枚举的
- 子假设 1.2：弹力设计模式集（重试/熔断/限流/降级/幂等/补偿）是"应对部分失败"的完备集
- 子假设 1.3：监控是弹力设计的前提而不是补充
- 动手验证：两服务故障注入压测（30% 随机失败 + 200ms 延迟抖动），对比"裸调用/只重试/重试+熔断"三种模式，预期看到"只重试"在 B 过载时雪崩
- 产出：故障类型 × 弹力模式矩阵图 + 200 字讲清"为什么只加重试可能让系统死得更快"
- DIKW 锚点：数据→信息

### W2：弹力设计（下）+ 管理设计——把故障关进笼子

- 子假设 2.1：幂等、状态、补偿事务是同一问题的三个视角
- 子假设 2.2：服务网格的本质是"把弹力设计从业务代码下沉到基础设施"，而非新技术（业务幂等管不了）
- 子假设 2.3：配置中心用 AP、分布式锁用 CP——这个 trade-off 是本周试金石
- 动手验证：Redis 分布式锁 + fencing token 实验，观察锁超时后没有 fencing token 时的数据损坏
- 产出：200 字讲解"服务网格为什么管不了业务幂等"
- DIKW 锚点：信息→知识

### W3：性能设计 + 结算场景映射——主场验证周

- 子假设 3.1：缓存的本质是"用一致性换性能"，结算场景的可缓存边界由业务容忍度决定
- 子假设 3.2：异步化的本质是"用时间换解耦"，代价是状态可见性延迟
- 子假设 3.3：秒杀的"削峰+排队+限流"三板斧与结算的"资金峰值防护"同构，差在"秒杀可以拒绝，打款不能丢"
- 动手验证：结算系统真实链路模式覆盖度体检（每个环节用了哪些模式、缺了哪些、缺的是有意还是疏忽）
- 产出：结算链路模式体检文档（L8/P7 面试可直接使用）
- DIKW 锚点：知识层夯实

### W4：编程范式 + Go 编程模式——代码层面的本质

- 子假设 4.1：编程范式之争的本质是"组合方式之争"，差异只在组合基元（对象/函数/类型）
- 子假设 4.2：Go 设计是"组合优先"哲学的极端化（委托优于继承、接口隐式满足、组合优于类型层级）
- 子假设 4.3：错误处理风格是范式的试金石——Go 选择显式返回错误 vs Java 异常背后的世界观
- 动手验证：用 Go 重写一个熟悉的 Java 小工具（带重试和规则过滤的结算数据清洗器），强制使用 Functional Options + Pipeline + 显式错误处理
- 产出："范式 × 组合基元 × 错误世界观"对照图 + 200 字回答"为什么陈皓说编程的本质是控制复杂度"
- DIKW 锚点：知识→智慧过渡

### W5：区块链 + 练级攻略对照 + 趋势预判——验收周

- 子假设 5.1：区块链的本质是"用算力成本换信任"，是分布式共识在拜占庭环境（参与者不可信）下的特例；PBFT/PoW 与 Raft/Paxos 差在参与者是否可信这一个变量
- 子假设 5.2：智能合约 = "规则引擎 + 不可变状态机"，和结算的规则引擎同构
- 子假设 5.3：练级攻略底层原理部分在 2026 年仍 100% 成立，工具链部分已被云原生 + AI 编程改写
- 动手验证：对 3 个 2026 年技术趋势（AI Agent 基础设施、WebAssembly 服务端化、结算实时化）各写一段 150 字预判，附带"什么证据会证明我错了"
- 产出：3 段可证伪预判 + 练级攻略过时度统计表
- DIKW 锚点：智慧层

## 验收标准（学完能回答的 5 个问题）

- Q1：从零设计日处理百亿资金的分布式结算系统，先定哪三个不可妥协的不变量（invariants）？
- Q2：面对新技术文章，判断框架是什么——它解决了故障矩阵的哪个格子？
- Q3：线上出现"打款重复但幂等键看似正常"故障，根因定位路径是什么？
- Q4：H1-H3 对了几个？错在哪？
- Q5：对"AI 原生时代的分布式基础设施"的具体预判是什么？什么证据会出现时承认判断错了？
