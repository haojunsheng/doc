## 核心论点

### 论点 1：公式三项缺一不可，但 Harness 是拉开生产差距的真正杠杆

**证据：**
- 消融实验 1-1（本章唯一硬因果证据）：同一模型，去掉上下文、工具结果或系统提示词中任何一块，系统显著退化
- LangChain Terminal Bench：无模型升级，Harness 优化使准确率 52.8% → 66.5%
- OpenAI 工程团队 10 倍效率不等模型升级

**证据强度：** 中等——消融实验是直接因果证据；Bench 数据是相关证据，未提供实验细节。

### 论点 2："RL 会吃掉 Harness"方向正确，但节奏很慢，业务语义层不可被吃

**论证结构：**
- 让步：模型规模增长终将覆盖通用约束（JSON 格式、基础校验）
- 防守：但业务语义层——"什么算对"——只有业务能定义，参数不可审计，只能活在外部产物路径
- 类比：Saltzer/Reed/Clark 1984 端到端论证——某些功能只能在端点实现

**证据强度：** 推理为主，无直接实验数据。读者贡献的"结算系统对账"类比构成支撑性旁证。

### 论点 3：ReAct 轨迹是状态机，代价是二次方增长

LLM 本身无状态——纯函数 `f(轨迹) → 下一步`，ReAct 循环+轨迹才是状态机。轨迹 append-only，每次调用重放全量历史，代价 O(n²)。第二章上下文工程一整章就是打这个靶子。

**读者同构：** append-only 日志 → 状态重建 → 随长度退化 = 区块链的设计（中本聪初始设计也是全量回放，后来通过快照/UTXO 修剪/轻节点解决）。关键差异：区块链需要多节点共识，Agent 只有一个大脑在读日志 → 压缩可以比区块链激进。

## 扩展公式：Agent = Model + Harness

Demo 视角 vs 生产视角的跃迁。约束/验证/纠正不是独立模块，是上下文和工具身上的工程实践。

### 范式演进

```
提示 ⊂ 上下文 ⊂ Harness ⊂ Loop 工程（层层包含）
```

| 范式 | 能力范围 | 示例 |
|------|---------|------|
| 提示 | 单轮指令控制 | 系统提示词 |
| 上下文 | 多轮记忆管理 | 消息列表、状态栏 |
| Harness | 约束/验证/纠正全链路 | 工具设计、护栏、评估 |
| Loop | 持续学习与进化 | 四种更新载体、评估回路 |

### 三原则

1. **简单**：能 API 不框架
2. **透明**：决策轨迹全可见 = 建立信任
3. **ACI 防呆**：从 Agent 视角设计接口（区别于 API 从程序员视角）；Poka-yoke 防呆——SIM 卡缺角/微波炉门没关好不加热

### 编排光谱

| 场景类型 | 模式 | 原因 |
|---------|------|------|
| 资金链路、结算 | 工作流 | 节点顺序不可变、攻击面收敛在节点内 |
| 用户意图理解、异常处理 | 自主模式 | 需要意图驱动、灵活响应 |
| 混合场景（n8n 模式） | 混合 | 两者共存 |

### 护栏三层

| 层级 | 防护对象 | 关键风险 |
|------|---------|---------|
| 输入侧 | 越狱/注入/审核 | 用户自己试图绕过模型安全限制 |
| 执行侧 | 工具风险评级 | 低/中/高工具调用的风险控制 |
| 输出侧 | PII/合规 | 敏感信息过滤、合规检查 |

**越狱 vs 提示注入的区别：** 前者用户自己绕限制，后者通过外部数据间接操纵。

**人工干预两种触发：** 超失败阈值 + 高风险操作。

## 学习机制三路径与三轴判据

全书的时间维度总图。三路径是动态公式 `Agent(t+1) = Agent(t) + 评估回路(Agent(t))` 的工程对应物。

### 三路径

| 路径 | 机制 | 适用场景 |
|------|------|---------|
| 上下文适应 | 通过上下文窗口传递信息 | 一次性、低频率、高表达性 |
| 外部产物 | 知识文档/Prompt/Skills/Harness | 结构性改变、可审计 |
| 参数更新 | SFT/RL 重新训练 | 深层能力提升、高成本 |

### 三轴分流判据

| 判据 | 作用 | 判断标准 |
|------|------|---------|
| 变化频率 | 定载体的"热"度 | 高频→上下文/外部产物；低频→参数 |
| 可显式表达性 | 定能不能进参数 | 难表达→外部产物；易表达→参数 |
| 可审计性 | 定必须留在哪 | 需审计→外部产物；无需→参数 |

**关键结论：** 业务语义层只能活在外部产物路径上，因为参数不可审计。

### 同构点

规则引擎（Aviator）的分流逻辑 = Prompt/Harness/参数的分流逻辑。

## 补丁层 vs 语义层二分

**本章最有原创价值的构造**——回击"RL 会吃掉 Harness"最强反驳。

### 二分结构

| 层次 | 定义 | 是否会被模型吃掉 | 例子 |
|------|------|----------------|------|
| 通用补丁层 | JSON 格式约束等，会被模型吃掉 | 是（迟早） | 输出格式校验、基础输入过滤 |
| 业务语义层 | "什么算对"只有业务能定义 | 否（结构上不可被吃） | 结算逻辑、合规判断、领域规则 |

### 端到端论证

Saltzer/Reed/Clark 1984 端到端论证在 Agent 场景的应用——某些功能只能在端点正确实现，下层做只能是性能优化。

## 消融实验 1-1

本章唯一硬因果证据：同一模型，分别去掉上下文、工具结果或系统提示词，系统显著退化。证明三者在 Agent 系统中的必要性。

## 实验数据

| 实验主体 | 对比对象 | 结论 |
|---------|---------|------|
| Kimi K3 | RL 内化的是"何时调用、怎么用"的决策策略，不是工具本身 | RL 内化决策策略，工具本身仍需 Harness |
| GPT-5.6 | 仅换模型不如换 Harness | 模型升级有边际效应，Harness 是更高效的杠杆 |
