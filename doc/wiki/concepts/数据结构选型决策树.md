# 数据结构选型决策树

## 核心论点

工程中不存在脱离场景的"最好数据结构"，只有场景约束的函数映射。这是整个计划的核心认知框架。

## 四个候选结构的核心差异

| 结构 | 查找 | 有序性 | 插入/删除 | 典型场景 |
|------|------|--------|-----------|----------|
| **散列表** | O(1) 均摊 | 无 | O(1) 均摊 | 快速查找、去重、缓存 |
| **跳表** | O(log n) | 有 | O(log n) | Redis zset、范围查询友好 |
| **红黑树** | O(log n) | 有 | O(log n) | JVM TreeMap、Java Collections |
| **B+ 树** | O(log n) | 有 | O(log n) | 数据库索引（MySQL InnoDB） |

## 选型的关键维度

1. **内存 vs 磁盘**：内存数据结构首选散列表/跳表/红黑树；磁盘/块存储首选 B+ 树
2. **有序性需求**：需要范围查询/有序遍历 → 排除散列表
3. **并发场景**：跳表实现简单、适合并发；红黑树旋转复杂、并发难度大
4. **缓存局部性**：数组/跳表优于链表；快排优于堆排（缓存友好）
5. **实现复杂度**：跳表比红黑树简单得多，这是 Redis 选跳表而非红黑树的核心原因

## Redis zset 的选型案例

Redis 选择跳表而非红黑树实现 zset，不是因为跳表性能更好，而是因为：
- 实现复杂度低（减少 bug 风险）
- 范围查询天然友好（链表结构）
- 查找性能与红黑树同阶 O(log n)
