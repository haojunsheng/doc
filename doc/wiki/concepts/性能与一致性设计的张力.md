# 性能与一致性设计的张力

缓存/异步等性能手段与结算"强一致"场景存在根本冲突。这是 W3 的核心发现。

## 核心洞察

| 性能手段 | 本质 | 结算场景适用性 |
|:---|:---|:---|
| 缓存 | 用一致性换性能 | 费率配置可缓存，账户余额不可缓存 |
| 异步 | 用时间换解耦 | 计费→清分可异步，清分→打款需谨慎 |
| 削峰排队 | 用时间换并发 | 大促打款峰值可用，但差在"打款不能丢" |

## 结算场景的特殊性

结算系统是"强一致 + 低并发（相对 C 端）+ 高正确性"场景，这与 C 端电商的"最终一致 + 高并发 + 可容忍少量错误"形成鲜明对比。同样的性能设计模式在不同场景下的适用性差异巨大。

## 与秒杀的同构性

[[秒杀与结算峰值的同构性]] 详细讨论了这一概念：秒杀的"削峰+排队+限流"三板斧与结算的"资金峰值防护"同构，差在"秒杀可以拒绝，打款不能丢"。
