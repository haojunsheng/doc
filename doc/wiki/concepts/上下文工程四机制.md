# 上下文工程四机制

## 定义

上下文工程通过四种机制各自解决一个独立问题，四者互不重叠，合起来覆盖上下文管理的全部主要挑战。

| 机制 | 解决的问题 | 本质 |
|------|-----------|------|
| 提示工程 | 提示词膨胀 | 在消息列表中插入指令、示例、约束，控制模型行为 |
| Skills 按需加载 | 工具列表膨胀 | 不一次性加载全部工具描述，只在需要时注入相关 Skills |
| 状态栏 | 环境不感知 | 在消息列表固定位置维护当前状态摘要，让 Agent 知道"现在在哪里" |
| 压缩 | 长度超限 | 将历史消息压缩为摘要，腾出上下文空间 |

## 为什么是四个而不是一个？

四机制对应四个独立问题，用一个方案解决不了所有问题：
- 提示工程治不了工具列表膨胀（工具描述太多，prompt 再精炼也没用）
- 压缩治不了环境不感知（压缩后历史没了，但状态栏是实时快照）
- Skills 加载治不了提示词膨胀（Skills 是模块化的，prompt 是全局的）

## 隔离优于压缩

当单 Agent 上下文压力大时，优先考虑拆分而非压缩——让多个子 Agent 各自只记各自的事，比单 Agent 记忆压缩更能保持上下文质量。参见 [[隔离优于压缩]]。

## KV Cache 工程约束

上下文前缀不能乱动——KV Cache 的存在意味着消息顺序和内容一旦确定，就不能在不触发缓存失效的情况下随意修改。这是上下文工程最重要的底层约束。

## 与提示注入的关系

提示注入是上下文工程的安全对偶面——凡是能进上下文的都是攻击面。上下文越开放，注入风险越大。

## 验证方式

- 跑 `chapter2/` 提示注入攻防实验，亲手注入成功一次
- 打印真实请求的消息数组，观察上下文实际结构
- 改动消息前缀，观察 KV Cache 失效带来的成本变化
