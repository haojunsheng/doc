# 实践在前，命名在后

## 核心主张

Agent 架构的好原则不是被发明的，是被真实业务倒逼出来的——它们先于名词存在，也穿越模型迭代周期。

## 证据：Pine 三例

[[Pine AI]] 的实战经历构成论证的实证基础：

| 实践 | 对应名词 | 出现先后 |
|------|---------|---------|
| 动态加载提示词 | Skill | 先于 Skill 名词流行 |
| 防护机制（幻觉/越权/危险处理） | harness | 先于 harness 名词流行 |
| 提议者-审核者（proposer-reviewer） | loop engineering | 先于 loop engineering 名词流行 |

## 行动推论

**等名词流行就慢一步。**

但这个推论需要限定前提：高要求的真实业务。

## 弱版与强版

- **弱版**（无人反对）：名词是滞后指标，已被业界普遍采用后才能称为名词。
- **强版**（需限定前提）：追名词是系统性错误，只在有大量真实业务场景的前提下成立。

对于大多数业务复杂度有限的从业者，追名词、看论文是理性策略——前提是带着背后的实践问题去读。

## 读者补丁：评估机制

针对"普通人业务没那么复杂"的反驳，作者给出对策：

> **评估机制 = 把小业务压缩出大业务失败密度的装置。**

一天暴露 1000 个失败 vs 1 个的装置，让"小业务"也能产出架构洞见。

## 与名词的关系（H2 修订）

参见 [[假设驱动学习计划-H1H2H3可证伪框架]] 中的 H2 修订：

> 名词是没有难业务的大多数人低成本继承实践的通道；但读名词时必须带着它背后的实践问题去读，否则拿到的只是词。

名词不是实践的替代品，而是**低成本继承通道**。

## 关键命题

**"系统的定义由'什么会出事'决定，不由'什么在实时跑'决定。"**

结算系统类比：对账不在交易实时链路里（常是夜间批处理），但没人敢说对账不是结算系统的一等组件。同理，评估回路不在 Agent 的实时推理链路上，但它是一等组件。参见 [[动态Agent公式]]。

## 强度说明

证据样本量为 1（同一家公司的三个例子），修辞上制造"模式重复感"而非独立统计证据。作为启发式主张成立，作为普遍命题需 W1–W3 各章进一步验证。
