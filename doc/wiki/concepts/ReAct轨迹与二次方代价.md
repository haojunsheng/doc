# ReAct 轨迹与二次方代价

## 定义

ReAct（Reasoning + Acting + Observing）循环中，Agent 的状态由轨迹（trajectory）维持。轨迹是 append-only 的消息日志，导致每次调用的代价随轨迹长度二次方增长。

## 核心机制

### LLM 是无状态的

LLM 本身是纯函数：`f(轨迹) → 下一步`

- 没有内部状态
- 每次调用都依赖完整的轨迹
- 轨迹 = 静态前缀（系统提示）+ 动态消息历史

### 轨迹的 append-only 特性

```
时间 t=1: [系统提示, 用户输入]
时间 t=2: [系统提示, 用户输入, 思考1, 行动1, 观察1]
时间 t=3: [系统提示, 用户输入, 思考1, 行动1, 观察1, 思考2, 行动2, 观察2]
...
```

每次调用都必须重放全量历史。

## 二次方代价

**问题：** 轨迹长度 O(n)，每次调用处理 O(n) 内容，总代价 O(n²)。

**表现：**
- 对话越长，单次调用越慢
- 上下文窗口有限，长对话会触发压缩
- 压缩丢失信息，导致性能下降

## 与区块链的同构

读者发现的重合点：

| 特性 | ReAct 轨迹 | 区块链 |
|------|-----------|--------|
| 数据结构 | append-only 日志 | append-only 链 |
| 状态重建 | 重放全量历史 | 重放全量交易 |
| 退化问题 | 随长度变慢 | 随长度变慢 |
| 解决方案 | 快照、压缩、轻节点 | 快照、UTXO 修剪、轻节点 |

**关键差异：**
- 区块链需要多节点共识
- Agent 只有一个大脑在读日志
- 因此 Agent 的压缩可以更激进（LLM 自动摘要）
- 代价是压缩可能丢失关键信息

## 第二章的靶子

ReAct 轨迹的二次方代价是第二章"上下文工程"要解决的核心问题：

| 机制 | 解决的问题 | 对应策略 |
|------|-----------|---------|
| 状态栏 | 环境不感知 | 维护当前状态摘要 |
| 压缩 | 长度超限 | 历史消息压缩为摘要 |
| Skills 按需加载 | 工具列表膨胀 | 只加载相关 Skills |
| 隔离 | 单 Agent 压力大 | 拆分为多 Agent |

## 实践含义

1. **轨迹管理是核心挑战**：不是"能不能跑通"，而是"能跑多远"
2. **压缩是双刃剑**：压缩可以延长对话，但可能丢失关键信息
3. **错误检测延迟**：压缩丢信息后，只能出错后发现——这是第六章"评估"要解决的问题
4. **架构选择**：长任务需要拆分，避免单 Agent 处理过长轨迹
