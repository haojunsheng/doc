# 弹力设计模式集

应对分布式系统"部分失败"的系统性手段集。这些模式不是孤立的技巧，而是同一件事（在不确定环境中用确定性原语把故障关进笼子）的不同切面。

## 模式清单

| 模式 | 针对的故障 | 核心机制 |
|:---|:---|:---|
| 重试 | 瞬时故障、网络抖动 | 失败后重复尝试，配合退避策略 |
| 熔断 | 持续性故障、级联失败 | 检测到故障后主动切断调用，防止雪崩 |
| 限流 | 过载、流量洪峰 | 限制并发或速率，保护下游 |
| 降级 | 非核心功能不可用 | 关闭非关键路径，保核心功能 |
| 幂等 | 重复请求、网络重试 | 保证重复操作不会产生副作用 |
| 补偿 | 操作失败后恢复 | 用反向操作撤销已完成的步骤 |

## 关键洞察

1. **只加重试会让系统死得更快**：当 B 服务过载时，A 的重试请求会进一步加重 B 的负担，形成雪崩效应。必须配合熔断和限流使用。
2. **监控是弹力设计的前提**：没有监控数据，熔断阈值、重试间隔等参数无法被正确设定。
3. **模式之间存在依赖关系**：重试需要熔断来兜底，熔断需要限流来保护下游，幂等需要补偿来处理失败。

## 与数据面/控制面的关系

弹力设计属于"数据面"——直接处理请求流转中的故障。[[数据面-vs-控制面]] 框架指出，数据面策略需要动态调整，这正是控制面（配置中心、服务网格）存在的唯一理由。
