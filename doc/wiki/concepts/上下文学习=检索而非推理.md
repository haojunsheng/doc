# 上下文学习 = 检索而非推理

## 定义

Attention 机制的本质是检索，而非归纳统计。上下文窗口是一台"只有一半的检索引擎"——擅长查找已有内容，不擅长主动计算统计量。这是 Agent 工程中所有上下文管理技术（状态栏、压缩、Skills）的设计底层。

## 核心洞察

用"笼子里有几只黑猫"做类比：
- 查找"笼子 37 里是什么猫"：注意力擅长，直接找到即可
- 数"100 个笼子里有多少只黑猫"：需要现算，而且会算错

前者是检索，后者是统计归纳——LLM 的注意力擅长前者，不擅长后者。当任务需要统计归纳时，如果不显式补充提炼层，模型要么靠思维链一步步现算（成本高且不可靠），要么出错。

## 设计含义

正因为上下文是"只有一半的检索引擎"，所有工程化信息管理本质上都是在补"提炼层"：

| 技术 | 做法 | 效果 |
|------|------|------|
| 状态栏 | 用代码把隐式状态提前算成键值对加入上下文 | 弱模型补准确率，强模型省一个数量级的思考量 |
| 压缩 | 把臃肿的原始记录换成提炼结论 | 保留必要信息，剔除噪音 |
| Skills | 按需加载，KV Cache 布局保住前缀 | 避免不必要信息占用上下文 |

## 与上下文漂移的关系

[[上下文漂移]] 的根因正是"上下文学习 = 检索而非推理"——中间步骤结果淹没目标不是因为"字太多"，而是因为检索系统里没有显式的"目标锚点"，模型只能被动地在上下文中"寻找"，越找越偏。

显式状态栏（把目标、进度、关键约束写成可检索的键值对）是缓解上下文漂移的直接手段。

## 与外部观测第三轴的关系

参见 [[外部观测第三轴]]——模型想不出的信息（真实时间、执行结果）必须靠外部仪器观测并写回，而不是在上下文里反复推理。

## 实践检查项

拿到一条 Agent 指令或一段上下文，默认检查："这条信息模型自己想不想得到？"
- 想得出来的（历史对话、任务指令）→ 替它省力，不是核心价值
- 想不出来的（真实时间、执行结果、系统状态）→ 值得注入，才是外部观测的价值
