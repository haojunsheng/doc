# Harness（可靠性机制）

## 定义

Harness 是围绕上下文与工具建立的约束、验证与纠正机制，而非模型本身。它是 Agent 可靠性的来源。

核心命题：**Agent = LLM + 上下文 + 工具**，三者缺一不可，但分量不等——上下文（"眼睛"）决定能力上限。Harness 的本质是对这三者的工程化管理，而非单纯依赖更强的模型。

## 三块咬合

Harness 不是单一技术，而是三块机制的咬合系统：

### 机制底座：上下文管理
- 上下文学习 = 检索而非推理（参见 [[上下文学习=检索而非推理]]）
- 状态栏、压缩、Skills 等工程化信息管理，给"只有一半的检索引擎"补提炼层
- 工具设计：模型感知到的世界与工具操作的世界不能有系统性偏差

### 手脚层：工具 + 代码
- 工具设计决定 Agent 能做什么
- **代码是元能力**：既完成任务，又积累知识、创造工具、优化自身
- Coding Agent 成熟不是代码模型强，而是软件工程几十年攒下的测试套件、类型系统、版本控制天然构成了一套 Harness
- 可靠性取决于每类故障是否有对应的检测、恢复与终止路径

### 评估闭环
- 观察 → 假设 → 实验 → 验证
- 运行经验写回四种载体：知识文档、Prompt、Skills、程序/参数
- 在线执行与离线学习分离，生成可验证、可回滚的候选更新

## 隔离优于压缩

参见 [[隔离优于压缩]]。当单 Agent 上下文压力大时，优先拆分任务给多个子 Agent（各自只记各自的事），而非让单 Agent 记忆压缩。（来源：notes/20260809T163426--拆书-AI-Agents-in-Depth__book.md）

## 关键证据

第一章消融实验提供直接因果证据：
- 同一模型，去掉上下文、工具结果或系统提示词中任何一块，系统显著退化
- 同一模型换 Harness，准确率从 52.8% 跳到 66.5%（OpenClaw 基准，后记实验）（来源：notes/20260809T163426--拆书-AI-Agents-in-Depth__book.md）
- 结论：可靠性来自模型之外的 Harness，而非模型本身

## 实践含义

- 判断 Agent 问题不再问"哪个模型最强"，先问"它看到什么、信息有没有被提炼、能不能核实"
- 任何一次优化之前，先立评估基线
- 把"模型会错"当默认前提，设计检测-恢复-终止路径，而不是事后打补丁
- 状态栏必须用代码维护而非让 LLM 批量统计
- 拿到信息先问："模型自己想不想得到？"想得出来的是省力，想不出来（真实时间、执行结果、系统状态）才值得注入
