# fencing token

分布式锁中的排他令牌机制，用于防止锁超时后客户端继续执行导致的数据损坏。

## 问题背景

Redis 分布式锁存在一个经典问题：客户端 A 获取锁后，因某种原因执行时间超过锁的 TTL，锁自动释放，客户端 B 获取锁并开始执行。此时客户端 A 恢复执行，会与客户端 B 并发操作共享资源，导致数据不一致。

## fencing token 机制

每个客户端在获取锁时获得一个单调递增的 token。执行临界区时，携带该 token 发送请求。服务端维护当前有效 token，只处理 token 不小于当前值的请求。这样，即使锁已过期，旧客户端的请求也会被拒绝。

## 实验要点

动手验证实验（W2）：
1. 用 Redis 实现带超时和 fencing token 的分布式锁
2. 故意制造锁超时但客户端继续执行的场景
3. 对比有/无 fencing token 时的数据一致性结果

这是"管理设计"篇最值钱的一个实验，直接演示了"控制面的一致性基础设施"的必要性。
