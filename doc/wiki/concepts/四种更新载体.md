# 四种更新载体

## 定义

Agent 持续进化的四种更新载体，按更新成本和风险从低到高排序。

## 四种载体

| 载体 | 描述 | 更新成本 | 风险 | 适用场景 |
|------|------|---------|------|---------|
| 知识文档 | FAQ、知识库、上下文提示 | 最低 | 最低 | 一次性知识注入，无需修改代码 |
| Prompt 与 Skills | 提示词模板、按需加载的 Skills | 低 | 低 | 行为模式调整，不影响模型本身 |
| 程序与 Harness | 代码逻辑、安全机制、验证流程 | 中 | 中 | 结构性改变，需要测试 |
| 模型参数 | SFT/RL 重新训练 | 最高 | 最高 | 根本性能力升级，周期长 |

## 关键原则

> 多数团队应该优先更新知识文档和 Prompt 而不是参数。

理由：
1. 更新成本差异巨大（分钟 vs 月）
2. 风险可控（回滚容易 vs 灾难性遗忘）
3. 业务响应速度（今天改明天上线 vs 下周才能上线）

## 与 Harness 的关系

Harness（可靠性机制）是程序与 Harness 这一载体的核心组成部分，负责约束、验证和纠正 Agent 行为。

## 灰度发布与回滚

灰度发布与回滚机制是把"进化"从冒险变成工程的关键——无论哪种载体，都应该有候选版本验证和快速回滚的能力。

## 验证方式

为一个假想业务（如客服 Agent）排定四种载体的采用顺序并给出理由。
