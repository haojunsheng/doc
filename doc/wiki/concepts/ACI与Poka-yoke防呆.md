# ACI 与 Poka-yoke 防呆

## 定义

**ACI（Agent-计算机接口）**：从 Agent 视角设计工具接口的方法论。区别于传统 API 从程序员视角的设计，ACI 关注的是 Agent 如何感知、理解和使用工具。

**Poka-yoke（防呆）**：丰田生产体系术语，指通过设计让错误无法发生。应用于 Agent 场景时，意味着工具接口设计应让 Agent 不容易调用错误、不容易传入错误参数。

## ACI 核心原则

### 从 Agent 视角设计

传统 API 设计假设使用者是程序员，了解数据类型、错误码、边界条件。ACI 设计假设使用者是 LLM，需要：
- 清晰的工具描述
- 自然的参数含义
- 可预测的错误反馈

### 防呆设计示例

| 场景 | 防呆设计 | 原理 |
|------|---------|------|
| SIM 卡缺角 | 物理缺口设计 | 方向错误时无法插入 |
| 微波炉门没关好 | 安全开关 | 门未关闭时无法启动 |
| Agent 工具调用 | 参数校验 + 默认值 | 必填参数缺失时返回明确错误 |
| 工具依赖顺序 | 前置条件检查 | 依赖未就绪时拒绝调用 |

## 与 API 设计的区别

| 维度 | API 设计 | ACI 设计 |
|------|---------|---------|
| 目标用户 | 程序员 | LLM/Agent |
| 错误处理 | HTTP 状态码、异常类型 | 自然语言错误描述 |
| 文档风格 | OpenAPI/Swagger | 工具描述、示例调用 |
| 参数约束 | 类型系统、Schema | 自然语言约束 + 可选校验 |
| 调试方式 | 日志、断点 | 轨迹回放、工具调用链 |

## 实践含义

- 工具描述本身就是 Harness 的一部分
- 好的 ACI 设计减少 Agent 调用错误的概率
- 防呆设计优于事后纠正——"让错误无法发生"比"发生错误后重试"更高效
